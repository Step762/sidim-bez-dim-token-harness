## Установка и запуск

Проверенная среда: Linux, Python 3.12, openJiuwen 0.1.20.post1.
Зависимости устанавливаются заранее. Локальные маршруты не требуют сети;
опциональный LLM-маршрут использует только заданный прокси.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
BUDGET=100000 .venv/bin/python -B run_agent.py --tasks-dir /path/to/tasks --disable-llm
```

Для предоставленных организаторами примеров и собственных проверенных
кодовых задач разрешён запуск с явным подтверждением доверия к коду:

```bash
BUDGET=0 .venv/bin/python -B run_agent.py --tasks-dir /path/to/trusted-copies --trusted-code
```

Без `--trusted-code` задачи `coding` пропускаются без запуска Python-кода.
Флаг не является песочницей. Не включайте его для произвольных финальных
задач до подготовки изолированного исполнения. Он задаётся оператором,
а не полями `task.json`. Прямой вызов `solve_coding` также требует `trusted=True`.

## Общий лимит времени

`runtime_limits.py` ограничивает весь запуск монотонным дедлайном. По умолчанию
это 3540 секунд от начала CLI, включая startup: остаётся 60 секунд до внешнего
часового timeout организаторов. `--time-limit` позволяет уменьшить этот срок,
но не увеличить его выше 3540. `--operation-timeout` по умолчанию равен 30 секундам.

Обнаружение/чтение задач, признаки планировщика, подготовка fallback, локальный
решатель и сохранение ответа ограничены синхронным Linux-таймером SIGALRM.
Ожидание workflow ограничено asyncio.timeout оставшимся временем операции и
запуска. Собственный сетевой таймаут шлюза 20 секунд сохраняется. Только
asyncio.timeout недостаточно: синхронный CSV/Markdown/Python блокирует event loop.

После таймаута локальной операции эта задача не повторяется через LLM. Следующие
локальные задачи продолжаются, если общий срок ещё не истёк. Уже опубликованные
answer.txt сохраняются; незавершённая атомарная запись не заменяет предыдущий
файл. Отмена модельного вызова сохраняет uncertain reserve в BudgetManager,
новых платных попыток после неизвестного расхода нет. Новые состояния:
timed_out и time_exhausted; runtime-отчёт отмечает истечение общего срока.

Ограничения рассчитаны на Linux и главный поток процесса. Это контроль времени
доверенного harness, не песочница для Python задачи. Длительное непрерываемое
ядром I/O и отказ файловой системы всё ещё требуют внешнего supervisor timeout;
официальный часовой timeout убирать нельзя. Наличие двух задач не меняет режим,
приоритеты, бюджет или запрет недоверенного coding.

## Docker и конкурсное исполнение

Образ собирается независимо от ноутбучной .venv:

```bash
docker build --progress plain -t sidim-bez-dim:harness-v8 .
```

База — официальный `python:3.12.12-slim-bookworm`, закреплённый digest
`sha256:593bd06efe90efa80dc4eee3948be7c0fde4134606dd40d8dd8dbcade98e669c`.
В requirements.txt зафиксированы все 169 пакетов, включая openJiuwen
0.1.20.post1. Сборка устанавливает готовые wheels и выполняет pip check.
Компиляторы, apt-установки и отдельная стадия сборки не понадобились.
Docker Hub и PyPI нужны при сборке; при исполнении установка отсутствует.

Проверенная локальная .venv занимает 910 МиБ; около 257 МБ приходится на
20337 файлов байткода. Крупные пакеты — transformers, pandas, openJiuwen,
numpy и matplotlib. Большинство входят в обязательное дерево зависимостей
openJiuwen, поэтому пакеты не удалялись ради уменьшения размера. Весов моделей
в образе нет. Размер уменьшают slim-база, отсутствие кеша pip и --no-compile.
Версии пакетов и содержимое базового образа закреплены; доступность этих
wheels в публичном индексе остаётся условием повторной сборки.

В .dockerignore действует разрешающий список из 16 файлов:
13 модулей приложения, requirements.txt, Dockerfile и .dockerignore.
Git, .venv, codex-local, AGENTS.md, .env, тесты, кеши и остальные файлы
не передаются в контекст. В Dockerfile также перечислены конкретные COPY;
копирования всего workspace нет. Ключи не передаются сборке через ARG/ENV.

ENV запрещает создание нового байткода; HOME, пользовательские кеши и
конфигурация matplotlib направлены в /tmp. Библиотеки Hugging Face работают
в offline-режиме и не скачивают модели. У LLM-шлюза сохраняется доступ
только к явно настроенному прокси. ENTRYPOINT — python, CMD —
`/app/run_agent.py --tasks-dir /data/tasks`; команда организаторов с явным
`--entrypoint python` также поддерживается.

Офлайн-проверка на заранее подготовленных временных копиях:

```bash
docker run --rm --pull=never --network none \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp -e BUDGET=0 \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --mount type=bind,source=/absolute/path/to/copies,target=/data/tasks \
  --workdir /app --entrypoint python \
  sidim-bez-dim:harness-v8 /app/run_agent.py --tasks-dir /data/tasks
```

Каталоги задач должны разрешать запись UID контейнера. База сохраняет
стандартный UID 0; при cap-drop ALL он не может обходить права чужих файлов.
Сценарий проверки меняет права только временных копий, не оригиналов.
Для собственного запуска можно явно подобрать --user под владельца mount;
условия доступа финального каталога задач нужно согласовать с организаторами.

Для конкурсной сети вместо --network none понадобятся предоставленная сеть
и `-e BUDGET -e LLM_BASE_URL -e LLM_API_KEY`. При полной конфигурации LLM
включится без дополнительных аргументов Python. `--disable-llm` принудительно
сохраняет офлайн-режим, BUDGET=0 запрещает запросы независимо от наличия ключа.
Работоспособность переключения проверяется на localhost, без реального прокси.

Полная воспроизводимая Docker-проверка:

```bash
.venv/bin/python -B tests/docker_smoke.py --image sidim-bez-dim:harness-v8
```

Для офлайн-проверки V2 №2 используется образ
`sidim-bez-dim:harness-v2-semantics-final`: тестовый слой поверх локального
`sidim-bez-dim:harness-v2-files-exact` с текущими 15 файлами приложения.
Сборка выполняется с --network=none и --pull=false без установки пакетов.
Временный контекст содержит только разрешённые файлы; исходная .dockerignore
копируется отдельно под именем input.dockerignore и затем в /app/.dockerignore,
чтобы legacy builder не добавил туда свою служебную строку. Контрольные суммы
всех файлов /app сравниваются с проектом. Для этого образа применяется та же
команда smoke с соответствующим --image. Такая проверка подтверждает текущий
код в прежнем окружении; полная сборка зависимостей по основному Dockerfile
заново не проверяется и потребует отдельного прогона перед сдачей.

Для V2 №3 используется тот же офлайн-метод: образ
`sidim-bez-dim:harness-v2-math` строится поверх локального
`sidim-bez-dim:harness-v2-semantics-final` с текущими 15 файлами приложения.
Проверка выполняется командой:

```bash
.venv/bin/python -B tests/docker_smoke.py --image sidim-bez-dim:harness-v2-math
```

Новых пакетов для арифметики нет; AST, Fraction и проверки лимитов используют
стандартную библиотеку. Совпадение исходников и образа проверяется по SHA-256.

Сценарий проверяет размер образа, pip check, read-only /app, запись в tmpfs
2 ГиБ, нулевые capabilities, no-new-privileges, отсутствие материалов/ключей
в приложении и окружении образа. Он запускает восемь примеров на копиях без
expected/check, отдельно с --trusted-code для доверенных примеров; проверяет
сохранённые исправления, неизменность тестов и обработку ошибок входа.
В конце все автоматические тесты выполняются внутри образа. tests/ и
codex-local/ для этого монтируются только для чтения и не входят в образ.
Тестовые HTTP-серверы доступны лишь на loopback контейнера с --network none.
Сценарий не использует Docker socket внутри контейнера и не меняет настройки
Docker Desktop, не удаляет посторонние контейнеры, образы или volumes.

### Почему недоверенный coding остаётся выключенным

Внешний контейнер ограничивает приложение относительно хоста. Произвольный
Python-тест внутри него всё ещё находится рядом с агентом: может пытаться
читать его окружение, использовать доступный агенту прокси и менять другие
задачи в общем writable mount. Таймауты и очищенное окружение дочернего
процесса не устраняют все эти возможности.

Нет Docker socket или CAP_SYS_ADMIN для вложенного контейнера; создание
непривилегированного user namespace зависит от seccomp и политики хоста.
Сценарий отдельно проверяет доступность unshare, не включая исполнение задач
по результату одной такой проверки. Наличие namespaces само по себе ещё
не доказывает готовность полной песочницы.

Проверенные в установленном openJiuwen провайдеры sandbox опираются на
отдельно развёрнутые сервисы/launcher, которых конкурсное окружение пока
не предоставляет. Не проверенная комбинация seccomp, Landlock и ограничений
Python здесь не выдаётся за полноценную изоляцию. В стандартном режиме
coding пропускается; --trusted-code никогда не включается автоматически.
V2 №4 подтвердил доступность Landlock ABI 3 и дополнительного seccomp,
но не полноценную изоляцию: недоверенное исполнение остаётся запрещённым.
Подробные измерения, сравнение трёх стратегий, ограничения статического ремонта
и проверки отказа описаны в [отчёте исследования coding](CODING_ISOLATION.md).
Диагностические пробы не являются песочницей и не включают coding автоматически.

Финальная команда запуска ожидается 9 ноября 2026 года. После публикации
нужно повторно проверить передачу BUDGET (её нет в старом примере команды),
права /data/tasks, сеть и точные ограничения CPU: в тексте регламента указано
4 ядра, в Docker-команде — 8. Проверки этого этапа используют 8 по уточнению
команды. Проверочный запрос к настоящему прокси требует отдельного разрешения.

Каталог задач должен содержать подкаталоги с `task.json`:

```text
tasks/
  task_a/
    task.json
    workspace/       # необязательные исходные файлы
    answer.txt       # создаётся после успешного решения
```

Входные поля: `task_type`, `instruction`, `reward`; при отсутствии `task_id`
используется имя каталога. Остальные поля не передаются решателю.
Ответ всегда записывается рядом с `task.json`, независимо от наличия `workspace/`.
Содержимое — итоговое число для `math` и скалярного `data_analysis`, JSON-объект
для поддержанной группировки CSV или точное значение факта для `search`,
без пояснений, с завершающим переводом строки.
Для `coding` сохраняются исправленный исходник в workspace и `DONE` в ответе,
после подтверждения успешного выполнения всех поддержанных тестов.

`BUDGET` принимается как неотрицательное целое число. Для локального запуска
его можно не задавать, пока LLM выключен. Локальные маршруты не расходуют
LLM-токены и работают при `BUDGET=0`. Для включения LLM нужен явный `BUDGET`.
Без дополнительных флагов модельный маршрут включён, когда непустые BUDGET,
LLM_BASE_URL и LLM_API_KEY переданы через окружение. При BUDGET=0 запросов нет.
При нулевом бюджете запросы заблокированы, включая прямой вызов шлюза.
Общий счётчик с резервированием реализован в `budget_manager.py`.
Планировщик `planner.py` сначала пробует локальные маршруты, затем выбирает
LLM-задачи по ожидаемым баллам на единицу расхода.

Код завершения: `0` — обработка закончена, в том числе с пропущенными задачами;
`1` — произошла ошибка чтения, исполнения или сохранения хотя бы одной задачи;
`2` — неверные параметры запуска. Ошибка отдельной задачи не останавливает
обработку следующих. Итоговые счётчики печатаются в стандартный вывод.

## Устройство

- `run_agent.py` — аргументы командной строки и запуск асинхронного процесса.
- `harness.py` — чтение задач, workflow openJiuwen, маршрутизация и сохранение.
- `safe_files.py` — ограниченное чтение обычных файлов и проверка каталогов.
- `plan_semantics.py` — независимый разбор поддерживаемого смысла LLM-задач.
- `math_solver.py` — разбор поддержанных условий и целочисленные вычисления.
- `search_solver.py` — чтение локальной базы знаний и переходы между сущностями.
- `data_solver.py` — разбор запросов, фильтрация и агрегирование CSV.
- `coding_solver.py` — ограниченные изменения Python-кода с проверкой тестами.
- `llm_gateway.py` — разрешённые модели, HTTP, таймауты и наблюдаемая статистика.
- `llm_fallback.py` — контекст задачи, JSON-планы и проверка их доказательств.
- `tests/test_harness.py` — проверки решателя, workflow, сохранения и CLI.
- `tests/test_search.py` — проверки поиска, изоляции баз знаний и пропусков.
- `tests/test_data.py` — проверки CSV, фильтров, агрегатов и ошибок данных.
- `tests/test_coding.py` — проверки исправлений, отката, ограничений и доверия.
- `tests/test_llm.py` — подменённый API и настоящий локальный HTTP-сервер.
- `requirements.txt` — зафиксированные зависимости проверенного окружения.

Для каждой задачи вызывается настоящий `Workflow.invoke` с отдельной сессией
`create_workflow_session()`. Движок openJiuwen исполняет граф
`Start → SolveTask → FallbackTask → End`, передавая входы и результаты через
`inputs_schema`. Узел `FallbackTask` возвращает локальный успех без обращения
к модели. Только после отказа он может вызвать шлюз и проверить план.
`SolveTask` наследует `WorkflowComponent`; его метод `invoke` выбирает решатель
из таблицы `SOLVERS`. Сейчас в ней все четыре типа. Маршруты `search`,
`data_analysis` и `coding` получают каталог текущей задачи через входы workflow.
Для `coding` тем же способом передаётся разрешение на доверенное исполнение.
Математический решатель сохраняет прежний интерфейс.

Использованный API проверен по установленному пакету и официальным исходникам:

- [Workflow и его публичные экспорты](https://github.com/openJiuwen-ai/agent-core/blob/develop/openjiuwen/core/workflow/__init__.py)
- [WorkflowComponent и контракт invoke](https://github.com/openJiuwen-ai/agent-core/blob/develop/openjiuwen/core/workflow/components/component.py)
- [Пакет openJiuwen в PyPI](https://pypi.org/project/openjiuwen/0.1.20.post1/)

Ветка `develop` в ссылках может меняться; воспроизводимость запуска определяется
зафиксированной версией пакета и автоматическими проверками.

Логи openJiuwen направлены только в консоль. Это исключает запись в `/app`,
который в конкурсном окружении доступен только для чтения.

Сохранение выполняется после каждой решённой задачи: запись во временный файл
в её каталоге, `flush` и `fsync`, затем атомарный `os.replace` в `answer.txt`.
Задача считается сохранённой только после успешной замены файла.

## Проверки недоверенных файлов

Корень tasks-dir определяется перед обнаружением задач. Вложенные каталоги
задач и task.json открываются без переходов по символическим ссылкам.
Ссылки на каталоги, включая внутренние псевдонимы одной задачи, отклоняются
отдельно и не останавливают обработку корректных задач. Повторные каталоги
проверяются по паре устройство/inode. Некорректный task.json увеличивает failed;
недопустимый файл данных приводит к пропуску задачи без нового answer.txt.

Общий модуль safe_files.py проверяет каждый компонент пути через дескрипторы
каталогов и O_NOFOLLOW. Для входного файла сначала проверяются тип и размер,
затем выполняется O_NONBLOCK-открытие и повторная проверка fstat. Поэтому
подмена обычного файла на ссылку или FIFO между проверкой и открытием
не перенаправляет чтение и не блокирует его. FIFO, устройства, сокеты,
символические и жёсткие ссылки не принимаются как входные файлы.
Политика запрета символических ссылок действует и внутри workspace.

Ограничения V2 задаются константами, а не условиями соревнования:

| Вход | Ограничение |
| --- | ---: |
| task.json | 1 МиБ |
| Один Markdown-документ | 1 МиБ |
| Сумма Markdown в одной базе | 16 МиБ |
| Число Markdown-документов | 1024 |
| Все элементы дерева базы | 4096 |
| Глубина вложенных каталогов базы | 32 |
| CSV | 64 МиБ |

CSV по-прежнему читается потоком, включая подготовку LLM-контекста.
Ограничение байтов проверяется при чтении, чтобы рост файла не обходил
проверку начального размера. Обнаруженное изменение размера или временных
метаданных во время чтения также отклоняется. Это не полноценный снимок
изменяемой другим процессом файловой системы.

На время запуска запоминаются идентификаторы корня и каталогов задач.
Подмена каталога после обнаружения отклоняется. Идентификатор планировщика
остаётся стабильным при изменении пути; формула выбора задач не менялась.
Создание временного ответа, замена answer.txt и уборка временного файла
выполняются относительно одного открытого каталога. Опубликованный ответ
имеет права 0644; ссылка на старый answer.txt заменяется без изменения её цели.

Этот слой рассчитан на Linux и защищает доступ к данным приложения. Он не
предоставляет песочницу для произвольного Python и не защищает от внешнего
процесса с правами менять mount или перемещать уже открытые каталоги.
Недоверенный coding остаётся выключенным. Общий таймаут локальных вычислений
и полноценная изоляция исполняемого кода требуют отдельных этапов.

Регрессионные проверки файлов:

```bash

```

## Поддерживаемая математика

Начиная с V2 №3 локальный решатель обрабатывает выражения с +, -, *, /,
скобками и обычным приоритетом операций. Поддержаны унарные знаки, целые
и десятичные числа, дроби как деление целых, а также обёртки What is,
Calculate, Compute и Evaluate. Например, What is 2 + 2? даёт 4,
2 + 3 * 4 даёт 14, а (2 + 3) * 4 — 20.

Поддержаны Add A and/to B, Subtract A from B, Multiply A by B, Divide A by B,
Sum/Difference/Product/Quotient of A and B. Операнды могут быть ограниченными
выражениями; числа словами zero–twelve распознаются без модели.
Последовательные команды и проценты используют те же math_spec и calculate_math,
что и LLM-валидатор V2 №2. Они тоже вычисляются бесплатно: Start with 10 coins.
Add 5 coins. Multiply by 3. даёт 45, Increase 200 by 5 percent. — 210.

V3-Q2 добавляет точное `Round -8.125 to two decimal places using round-half-up.`
Результат — `-8.13`: ровная половина округляется от нуля. Поддержаны десятичный
литерал и явно заданные 0–100 десятичных мест (zero–twelve либо цифры).
Вычисление использует Fraction, без float; нулевые конечные разряды не дописываются.
Неуказанный режим, другой режим, выражение вместо литерала и дополнительные
операции не угадываются. Эта локальная форма не расширяет LLM-схему.

Сохранён прежний английский шаблон о запасах коробок на складе:
начальное целое количество, последовательные отгрузки за несколько дней,
поставки, деление между складами с округлением вниз и удвоение запасов.
Числа берутся из инструкции, операции выполняются в указанном порядке
обычным Python. Текст инструкции не передаётся в `eval`, shell или `exec`.

Выражение разбирается ast.parse с режимом дерева выражения. Разрешены только
числовые Constant, BinOp с Add/Sub/Mult/Div и UnaryOp со знаком плюс/минус.
Дерево не компилируется в исполняемый код. Числовые константы читаются из
исходного написания и преобразуются в Fraction, поэтому 0.1 + 0.2 точно равно
0.3. Вызовы, имена переменных, атрибуты, индексы, импорты, строки, комментарии,
степени, целочисленное деление и остаток не поддерживаются.

Лимиты реализации: инструкция — 8000 символов, одно выражение/операнд — 2048,
числовой литерал — 80, дерево — 256 узлов и глубина 32. Числитель и знаменатель
промежуточного результата ограничены 2048 битами. Проверяется глубина скобок
до AST-разбора. Последовательных операций — до 16, складских — до 64.
Превышение лимитов и деление на ноль приводят к отказу без answer.txt.

Регламент и целочисленные примеры не задают общий формат нецелых ответов.
Соглашение реализации: целое без .0; конечная десятичная дробь без округления;
иначе сокращённая дробь p/q. Поэтому 1/3 + 1/6 сохраняется как 0.5 (= 1/2),
а 1/3 — как 1/3. Это допущение, совместимость со скрытым проверяющим нужно
уточнить. Явные неизвестные требования округления не игнорируются.
CSV-решатель сохраняет свои прежние правила форматирования.

Каждая операция и остаток инструкции должны полностью соответствовать
поддержанному формату. Неизвестная формулировка, отсутствующие величины
или деление на ноль приводят к `skipped` без создания `answer.txt`.
Это консервативный отказ от решения; он не доказывает невыполнимость задачи.

Существующие ответы при пропуске не удаляются. Для нового прогона следует
использовать свежие рабочие копии задач. Успешный повторный запуск атомарно
обновляет ответ. Произвольные математические условия пока не поддерживаются.

Ограниченный fallback принимает обёртку Solve the following arithmetic: перед
последовательной задачей. Локальная внешняя грамматика такую обёртку пока не
разбирает; LLM получает шанс при наличии полного резерва. После снятия обёртки
операции проверяет тот же math_spec. Произвольный Python от модели запрещён.
Неизвестное выражение без независимо проверяемого смысла пропускается.

Воспроизводимый независимый отборочный набор:

```bash
.venv/bin/python -B tests/test_math_extended.py --pairs
.venv/bin/python -B -m unittest discover -s tests -p test_math_extended.py -v
```

В наборе 28 пар: 20 полностью локальных, 2 смешанные с mock-LLM, 4 намеренно
отказные, одна с недостаточным бюджетом и одна с ошибочным модельным планом.
Эталоны находятся только в тестовом оценщике. Для проверки fallback прежние
LLM-тесты используют указанную обёртку, чтобы новый бесплатный решатель не
обходил проверяемый узел. Семантические отрицательные проверки сохранены.
Поддержка арифметики не гарантирует допуск: недоверенный coding отключён,
search и data_analysis также имеют ограниченные грамматики.

## Локальный поиск

Каждый вызов `search` читает только `workspace/kb/**/*.md` текущей задачи
и создаёт отдельный индекс. Имена файлов не задают сущность: её имя берётся
из заголовка первого уровня `# Имя`. В одном файле может быть несколько таких
разделов. Поддерживаются строковые поля `Born`, `Founded`, `Headquarters`,
`Employer`, `Mentor`, а также явные псевдонимы `Alias` в формате `Поле: значение`.
Несколько Alias одной сущности допустимы. Псевдоним разрешается только при
единственном владельце; столкновение с другим Alias или настоящим именем
не разрешается в пользу одного документа. Учитываются все объявленные Alias,
включая записи из противоречащих дубликатов; неявные прозвища не угадываются.

Вопрос разбирается в конечное поле и цепочку связей. Например, запрос города
работодателя наставника означает `Mentor → Employer → Headquarters`.
Количество переходов определяется вопросом; общая база между задачами
и автоматический обход всего графа не используются.

Поддерживаемые английские формулировки (вместо `X` — имя или цепочка
вида `Lena Noor's mentor's employer`):

- `In which year was X born?`, `What year was X born?`, `When was X born?`
- Те же три варианта с `founded` для года основания.
- `In which city is the headquarters of X?`
- `Where is X headquartered?`, `In which city is X headquartered?`
- `Who/What is X's employer?`, `Who/What is X's mentor?`
- `Who/What is the employer of X?`, `Who/What is the mentor of X?`
- `Which company does X work for?`
- `Who is mentored by X?` — единственный обратный Mentor, только локально.

Распознаются вопросы отдельно и стандартная служебная обёртка примеров.
Регистр и пробелы имён нормализуются при поиске; значение ответа сохраняется
в исходном регистре. Год должен быть одним числом из 1–4 цифр. Переходы
между сущностями поддержаны для `Employer` и `Mentor`, включая несколько
последовательных переходов и прямой/типографский апостроф в конструкции `'s`.
Alias разрешаются и в промежуточных связях. Буквальное имя или Alias не могут
скрыть другое допустимое выражение отношений. LLM-валидатор повторно проверяет
subject/chain/field по свежим документам перед приёмкой плана.

Для обратного Mentor требуется известная сущность X, ровно один явно
подтверждённый кандидат и одно точное написание его заголовка. Противоречивые
определения или явно неизвестные Mentor приводят к отказу; произвольного
обращения других отношений, объединения одноимённых людей и выбора первого
подходящего ответа нет. Пропущенное поле не превращается в доказанный факт.

Отсутствие базы, сущности, поля или целевого документа, неизвестное значение,
разные значения одного поля либо различающиеся определения одной сущности
приводят к `skipped`. Одинаковые определения не считаются конфликтом.
При неоднозначной связи задача пропускается даже тогда, когда альтернативные
пути могли бы дать одинаковый ответ. Для пропущенной задачи ответ не создаётся.

Содержимое Markdown обрабатывается как данные: только заголовки и известные
поля участвуют в поиске. Прочий текст, цитаты и ограждённые блоки кода не
становятся командами. Ссылки на документы за пределами базы не читаются.
Данные не передаются внешним сервисам, дополнительные зависимости не нужны.

Не поддерживаются произвольный естественный язык, поиск по части имени,
неявные связи, расчёт возраста, списки ответов, факты в свободном тексте,
таблицах или Markdown-ссылках вместо простых значений полей. Неизвестная
формулировка пропускается без попытки угадать ответ.

Отдельный `diagnostics.static_coding` — отключённый по умолчанию review-only
пилот C3. Он не входит в конкурсный образ и не импортируется production-harness.
Он не запускает файлы/тесты задачи и не пишет DONE: даже полиномиальное
соответствие внешнему integer-контракту не подтверждает конкурсное решение.
Границы описаны в [отчёте C3](reports/cycle_c3_coding_pilot_2026-11-08.md).

## Локальный анализ CSV

`data_analysis` читает указанный в инструкции CSV только из собственного
`workspace/`. Имя файла обязательно: подстановка `sales.csv` и выбор первого
найденного CSV не применяются. Поддерживаются относительные пути внутри
workspace; выход через `..`, абсолютные пути и внешние файловые ссылки запрещены.

Поддержаны инструкции с префиксом `The file inventory.csv.` либо с описанием
столбцов и количества строк, как в примерах. Реальные заголовки CSV определяют
доступные столбцы. Описанное в инструкции количество строк не заменяет чтение
файла и не используется для вычисления ответа.

Запрос из примеров разбирается в сумму указанного столбца, равенство по
строковому полю и включительный диапазон. Имена товара, столбцов и числа
извлекаются из инструкции. Например:

```text
The file inventory.csv. How many quantity of item 'gear' were sold in periods 2 through 4 inclusive?
```

Окончание множественного числа (`periods` → `period`) сопоставляется с реальными
заголовками. Если в CSV есть оба варианта, задача пропускается как неоднозначная.

Дополнительно поддерживаются явные запросы:

```text
The file inventory.csv. What is the sum of quantity where item = 'gear' and period between 2 and 4 inclusive?
The file inventory.csv. What is the average of price where quantity >= 10?
The file inventory.csv. How many rows are there where item != 'gear'?
```

Операции: `sum`, `count`, `min`/`minimum`, `max`/`maximum`, `avg`/`average`.
`count of COLUMN` считает подходящие строки с проверкой непустого значения
этого столбца; `How many rows are there` считает строки без целевого столбца.
Операция без `where` применяется ко всем строкам. Распознаётся стандартная
служебная часть инструкции из примеров.

Фильтры объединяются `AND` либо ограниченным локальным `OR` (цикл C4).
Например: `What is the sum of quantity where period = 2 or period = 6?`
Разрешено до 8 явных OR-альтернатив простых сравнений или включённых BETWEEN.
Каждая строка учитывается один раз, даже если совпали несколько альтернатив.
AND внутри `between A and B inclusive` относится к самому диапазону.
Смешанный логический AND/OR, скобки, NOT/XOR и неявные приоритеты не поддержаны:
агент отказывается вместо выбора предполагаемого порядка вычислений.
Строковые значения задаются в одинарных
или двойных кавычках; кавычка внутри значения может удваиваться. Сравнение
строк точное, включая регистр и внутренние пробелы. Для строк доступны `=` и `!=`,
для чисел — также `<`, `<=`, `>`, `>=`. Диапазон `between A and B inclusive`
включает обе границы; обратный диапазон и диапазон без явного `inclusive`
не интерпретируются по предположению.

Чтение построчное, через `csv.reader(strict=True)`, с запятой как разделителем.
Поддержаны UTF-8 с BOM и без, CRLF, пустые физические строки, запятые, кавычки
и переносы строк внутри корректно заключённых в кавычки полей. Большая таблица
не собирается в список и не отправляется модели.

Числа — целые и десятичные с точкой и необязательным знаком. Вычисления
выполняются точно через `Fraction`, без ошибок двоичного `float`.
Экспоненциальная запись, разделители тысяч, `NaN` и бесконечности не поддержаны.
Все числовые поля, используемые запросом, проверяются во всех строках,
включая строки вне выборки. Остальные поля читаются как строки: типы
не угадываются по названиям столбцов.

Для пустой выборки `SUM` и `COUNT` равны `0`; `MIN`, `MAX` и `AVG` не определены,
поэтому задача пропускается. Ответ записывается целым числом или точной
конечной десятичной дробью. Например, среднее `0.1` и `0.2` даёт `0.15`.
Если среднее требует бесконечной дроби, например `1/3`, и точность в инструкции
не определена, ответ не создаётся: правило округления не подставляется.

Повреждённые строки, отсутствующие или повторяющиеся заголовки, неверные
числа в задействованных полях, недоступный CSV и неизвестные запросы приводят
к `skipped` без создания ответа. Частичная сумма не сохраняется, пока не
прочитан и проверен весь файл. `expected` и `check` в решении не участвуют.

В цикле C1 добавлена локальная группировка по одному столбцу:

```text
Using ledger.csv, return a JSON object mapping each team to its total amount.
Using ledger.csv, return a JSON object mapping each team to its average amount where day >= 2.
Using ledger.csv, return a JSON object mapping each team to its row count.
```

В этой полной формулировке поддержаны total/sum, count, min/minimum,
max/maximum и avg/average; перед столбцом допустимо `of`. Фильтры — прежние
явные AND-сравнения, ограниченные OR-альтернативы и включённые диапазоны.
`row count` считает строки,
`count amount` — значения столбца и отказывается при пустом значении.
Ключи групп остаются точными CSV-строками: `01`, `1`, `1.0` различаются;
пустой или состоящий только из пробелов ключ приводит к отказу. Нет угадывания
типов, NULL или пропуска повреждённых чисел. Числа JSON точные, без float;
бесконечная десятичная дробь без правила округления не выводится. Пустой набор
наблюдаемых групп даёт `{}`, не создавая отсутствующие группы. Ключи объекта
сериализуются в стабильном порядке, это не поддержка сортировки строк по запросу.
Лимит — 10000 наблюдаемых групп; таблица читается потоком, в памяти только
агрегаты групп. Общий deadline и безопасное чтение действуют без изменений.
GROUP BY в LLM-схему не добавлен: неподдержанная групповая формулировка
не превращается моделью в скалярную операцию. Совместимость JSON с финальным
скрытым оценщиком остаётся вопросом организаторам.

LLM-схема остаётся conjunction-only: `_filters` и `_question` по умолчанию
не принимают OR. Неподдержанный модельный план не заменяет OR набором AND.
Новый OR вычисляется только локально тем же CSV-проходом, без LLM.

C5 также локально распознаёт узкую перефразировку:
`Calculate the total amount in ledger.csv where zone is 'blue' and step at least 2.`
Имена файла и столбцов, строковый литерал и числовая граница берутся из инструкции;
`at least` включает границу. Это SUM с двумя AND-условиями, исполняемый прежним
потоковым CSV-маршрутом. Дополнительный текст, замена AND на OR, другая операция
или неопознанное сравнение в этой конструкции приводят к отказу. Прежние формы
AND/OR, обработка пропусков и семантическая проверка LLM-планов сохраняются.

V3-Q2 поддерживает ограниченный выбор первой строки:
`In ranks.csv, sort by score descending and label ascending to break ties. Return the label of the first row.`
Допустим также префикс Using. Оба направления — ascending/descending;
первый ключ должен содержать корректные десятичные числа (до 80 символов), второй —
текстовые метки (до 512). Файл читается одним проходом без полной сортировки.
Без явного слова `lexicographically` второй ключ ограничен печатным ASCII-текстом
с буквами в одном регистре, без внешних пробелов. Числовые ID, смешанный регистр
и Unicode требуют явного `label lexicographically ascending`: это порядок
строк Python по Unicode code points, без локали и естественной сортировки.
При полном равенстве ключей результат допускается только для одинакового
возвращаемого значения. Пустая таблица, повреждённые строки/числа, пропуски,
неизвестные поля и дополнительные условия приводят к отказу целиком.
Возвращается точная исходная строка выбранного поля. LLM-контракт не меняется.

Произвольные перефразирования, смешанный AND/OR, группировки по нескольким столбцам,
DISTINCT, медиана, другие формы сортировки, объединение файлов, формулы
вроде `units * price`, иные разделители CSV и неявные преобразования типов
пока не поддерживаются.

## Исправление доверенного Python-кода

V1 распознаёт шаблон инструкции, который явно указывает Python-скрипт тестов
и один исходный модуль, как в конкурсных примерах. Имена файлов могут меняться;
поддержаны только имена в корне workspace. Команды из произвольного текста
инструкции не выполняются. `expected` и `check` не используются.

Исходный модуль разбирается через `ast`. Генератор пробует по одному локальному
изменению внутри функций: `+ ↔ -`, `* ↔ /`, `// → *`, противоположное направление
сравнения, `== ↔ !=`, `sorted ↔ reversed` для простого вызова встроенной функции.
Имена функций, переменных и значения констант не подменяются. Меняется только
соответствующий фрагмент исходника; другие фрагменты сохраняются. Новую
категорию исправлений можно добавить в генератор `_mutants`.

Сначала запускаются исходные тесты. Каждая следующая попытка получает отдельную
свежую временную копию Python-файлов workspace. Принимается только изменение,
при котором число тестов сохраняется, а множество неуспешных проверок строго
уменьшается без новых ошибок. Так можно последовательно исправить несколько
независимых ошибок. Промежуточные улучшения не записываются в исходный workspace.

После полного успеха выбранный вариант ещё раз проверяется в новой копии.
Проверяется неизменность тестов и других Python-файлов, а также отсутствие
посторонних изменений исходного workspace. Только затем исправленный модуль
атомарно заменяется с сохранением прав доступа; harness сохраняет `DONE`.
Если подходящего варианта нет, исходники задачи остаются прежними и ответ
не создаётся. Уже корректный модуль может пройти проверку без изменений.

Исполнение ограничено константами в `coding_solver.py`:

- Один запуск тестов — до 2 секунд.
- Общий вывод stdout и stderr — до 64 КиБ; избыток прекращает запуск.
- До 40 запусков, включая исходную и финальную проверки.
- До 4 последовательно принятых изменений и до 20 секунд на поиск в задаче.

Используется `subprocess.Popen` со списком аргументов, без shell. Процесс
получает минимальное окружение без API-ключей родителя, отдельную группу
процессов и отключённый stdin. При остановке завершается эта группа.
Распознаётся стандартный итог `unittest`: нулевое число тестов, пропущенные
проверки, неполный вывод и неподдерживаемые тестовые раннеры не считаются успехом.

Символические ссылки в workspace не поддержаны. В попытки копируются только
Python-файлы; задачи с внешними ресурсами или непереносимыми зависимостями
могут быть пропущены. Синтаксические ошибки, изменения интерфейсов, сложные
алгоритмы, правки нескольких модулей и исправления, требующие временно ухудшить
результат тестов, пока не поддерживаются. Успех видимых тестов не является
доказательством прохождения скрытых проверок.

Ограничения подпроцесса контролируют время и вывод, но не запрещают все
возможные действия самого Python-кода. Сейчас разрешено только доверенное
исполнение на рабочих копиях. Изоляция произвольных задач остаётся отдельным
задачей: внешняя Docker-упаковка сама по себе не изолирует код от агента.

## Ограничения текущего этапа

Исполнение последовательное; порядок выбирает планировщик без LLM-оценки задач.
Все LLM-запросы используют единый объект бюджета. Неопределённый расход
останавливает дальнейшие модельные вызовы, сохраняя локальную обработку.

Docker-упаковка добавлена; условия и проверки приведены ниже. Изоляция
недоверенного coding и сбор траекторий модельных вызовов ещё не реализованы.
Полную готовность к конкурсному прогону этот этап не заявляет.

## Опциональный LLM-маршрут

В стандартной команде LLM включается автоматически, если переданы непустые
`BUDGET`, `LLM_BASE_URL` и `LLM_API_KEY`. При неполном окружении остаются
локальные маршруты. `--enable-llm` требует явной конфигурации и сохраняет
прежний режим запуска. `--disable-llm` имеет приоритет над окружением;
оба флага одновременно запрещены. Некорректный BUDGET не обходится даже
при выключенной LLM. Адрес и ключ читаются исключительно из окружения,
без значений провайдера по умолчанию.
Реальный провайдер на текущем этапе не вызывается; включение против настоящего
прокси требует отдельного разрешения на проверочный запрос.

Подтверждённый организаторами контракт: Chat Completions, POST
`<LLM_BASE_URL>/chat/completions`, Bearer-авторизация и JSON. Базовый URL должен
включать нужный префикс версии API. Полный адрес, заканчивающийся на
`/chat/completions`, также поддержан. URL с пользовательскими данными,
query-параметрами или fragment отклоняется. Перенаправления и настройки
HTTP-прокси из окружения не используются.

Шлюз использует уже установленный `httpx`. Контракт дополнительно проверен
на том же локальном сервере через настоящий `OpenAIModelClient` версии
openJiuwen 0.1.20.post1, с `ModelClientConfig`, `ModelRequestConfig` и `invoke`.
В рабочем процессе вызовом адаптера управляет асинхронный узел openJiuwen.
Проверка на локальном сервере не утверждает доступность реальных моделей.

Выбор модели задаётся `--llm-model`. По умолчанию используется
`qwen3.6-35b-a3b-noreason`. Разрешены только:

- `qwen3.8-27b`
- `qwen3.8-27b-noreason`
- `qwen3.6-35b-a3b`
- `qwen3.6-35b-a3b-noreason`

До проверки контракта реального провайдера варианты с рассуждениями
отклоняются до HTTP-запроса. Передаваемый `max_tokens` пока нельзя считать
подтверждённой границей скрытых рассуждений. Программная `AccountingPolicy`
позволяет подключить проверенный контракт: включает ли completion рассуждения
и ограничивает ли параметр выхода всю генерацию. Сейчас такой контракт явно
задаётся только в тестах mock-сервера; инструкции задач его менять не могут.

Параметры: `--llm-timeout` — общий таймаут запроса, по умолчанию 20 секунд;
`--llm-max-tokens` — запрашиваемый предел ответа, по умолчанию 1024, допустимо
1–4096. Размер полученного HTTP-ответа ограничен 128 КиБ, контекст — 18000
символами. Вызов содержит системные правила и контекст одной задачи; история
предыдущих задач не передаётся. Кеш провайдера не считается экономией бюджета.

На задачу допускается один LLM-запрос, без автоматических повторов.
Ошибки 401, 403 и 429 блокируют дальнейшие запросы этого шлюза в текущем
прогоне. Таймаут, 500, неверный JSON или незавершённый ответ означают пропуск
задачи. Тексты ошибок провайдера, ключ и тело HTTP-ошибки не выводятся.
Если локальный решатель уже нашёл повреждённые данные или отсутствие нужного
факта, либо подготовка контекста обнаружила отсутствующие файлы/противоречия,
запрос не отправляется. При существующем `answer.txt` резервный запрос также
не выполняется; локальный решатель по-прежнему может проверить задачу заново.

Модель возвращает JSON-план, а не готовый ответ или программу:

- `math`: начальное число, не более 16 последовательных операций и точные
  цитаты из условия. Поддержаны сложение, вычитание, умножение, деление и
  округление частного вниз, процент от числа, увеличение и уменьшение на процент.
  Операции и порядок операндов разбираются из целых предложений независимо от
  плана. Цитаты подтверждают соответствующие фрагменты; считает Python через Fraction.
- `search`: сначала локально выбирается одна упомянутая сущность и нужные
  связи. Модель получает только соответствующие поля не более 8 записей,
  с цепочками до 3 переходов. Порядок цепочки устанавливается из вопроса;
  произвольные перестановки не допускаются. План задаёт путь и точный ответ. Значения,
  отсутствие конфликтов и совпадение ответа заново проверяются по файлам.
- `data_analysis`: модель видит имя CSV, реальные заголовки и число строк,
  без содержимого таблицы. План задаёт агрегат и до 8 фильтров с цитатами.
  Агрегат, целевой столбец и каждое типизированное условие независимо разбираются
  из вопроса. Обе границы интервалов проверяются отдельно. План преобразуется в язык запросов,
  который исполняет локальный CSV-решатель. Python и SQL от модели запрещены.
- `coding`: автоматический LLM-запрос в workflow пока не выполняется, поскольку
  произвольный предложенный код нельзя безопасно проверить без изоляции.
  Подготовлен отдельный асинхронный API `propose_coding(..., trusted=True)`:
  он возвращает предложение для просмотра, проверив структуру, имя модуля
  и синтаксис. Предложение не применяется, не исполняется и не создаёт `DONE`.
  Режим `--trusted-code` сохраняется для прежнего локального решателя.

Повторяющиеся JSON-ключи, дополнительные поля плана, неподтверждённые ответы,
команды, пропущенные условия и неподдерживаемые операции отклоняются.
Модель может вернуть `{"status":"unsolvable"}` — это обычный пропуск.

Семантика проверяется ограниченными грамматиками, а не совпадением множеств
чисел и слов. Это не доказательство смысла произвольного естественного языка.
Сложные условные математические
задачи, нестандартные связи, свободный текст в базе знаний, неоднозначные
агрегаты и планы без проверяемых оснований пропускаются. Неопределённое
округление, научная запись чисел, большие числовые литералы и неподдерживаемые
формулы также не превращаются в предполагаемый ответ.

V2 использует прежний JSON-формат начального числа и шагов. Для процентов
добавлены операции increase_percent, decrease_percent и percent; value содержит
ставку, например 5. Разрешён и эквивалентный множитель: для «Increase 200 by 5 percent»
шаг increase_percent со ставкой 5 и шаг mul со значением 1.05 дают 210.
Простое add 5 отклоняется. Поддерживаются последовательные изменения процентов,
«Subtract 5 from 20», «Divide 12 by 3» и «Divide by 2 rounded down» после начального
значения. Числа могут быть десятичными или словами zero–twelve. Произвольные
вложенные выражения, процентные пункты, неявное сложное начисление процентов
и неизвестные команды не поддерживаются. Нейтральные метаданные разрешены
только как однословные значения меток Background, Context, Ledger, Reference,
Label и Identifier. Дописанное условие после служебных указаний отклоняется;
стандартные указания и пример echo 42 не попадают в математические операнды.

Для CSV поддержаны прежние явные запросы локального решателя и команды
Calculate/Compute/Get/Find/What is с sum/total, count, min/minimum, max/maximum,
avg/average/mean, целевым столбцом и явно указанным CSV. Возможны отсутствие
фильтра, for all rows, один фильтр или AND-конъюнкция. Поддержаны числовые
сравнения знаками и словами at least, at most, above, below и другими явными
вариантами; строковые равенства и неравенства требуют кавычек. Диапазоны
between/from/through требуют inclusive или exclusive. Смешанные границы
задаются отдельными сравнениями, например month > 4 and month <= 6.
Сравниваются предикаты (столбец, знак, тип, значение), включая кратность;
порядок AND-фильтров не важен. month = 5 эквивалентен двум включительным
границам 5–5, а один month >= 5 не эквивалентен этому диапазону.
COUNT столбца и COUNT строк различаются. OR, группировки, формулы из нескольких
столбцов и неизвестные уточнения приводят к отказу без предполагаемого ответа.

Для поиска сохраняются прежние вопросы и поддерживаются What/Which city is X
based/located/headquartered in, Where is X based, What is the birth year of X.
Выражения X's mentor's employer и the employer of the mentor of X задают
mentor → employer; обратная формулировка задаёт другой порядок. Проверяются
именно эти переходы и конечное поле. Неявные обратные связи, например
«наставник одного из работников компании», не выводятся из найденного пути.
Неоднозначные вопросы и цепочки более трёх переходов отклоняются.

Положительные и отрицательные интеграционные проверки:

```bash
.venv/bin/python -B -m unittest discover -s tests -p test_semantics.py -v
```

Они используют настоящий workflow, локальный HTTP-сервер и MockTransport.
Валидация не выполняет дополнительных модельных запросов. Ошибочный план
с достоверным usage учитывается в бюджете даже при отказе от записи answer.txt.
С V2 №3 распознаваемые последовательные арифметические задачи и проценты
решаются локально. LLM-тесты явно используют ограниченную внешнюю обёртку,
чтобы продолжать проверять валидацию и учёт реальных mock-запросов.

Проверяются стандартные `prompt_tokens`, `completion_tokens`, необязательный
`total_tokens` и детализация рассуждений. Неизвестные дополнительные поля
безопасно игнорируются. Несогласованные счётчики отклоняются. Подтверждённый
usage учитывается до проверки содержимого ответа: неверный план или
незавершённый ответ с достоверным usage всё равно расходует бюджет.

## Единый бюджет LLM

CLI создаёт один `BudgetManager` и передаёт его шлюзу и workflow. Лимит берётся
из фактического `BUDGET`; автоматической подстановки 100000 нет. Некорректное
значение означает ошибку конфигурации. Без BUDGET разрешён только локальный
запуск с отключённым модельным маршрутом. Самостоятельный шлюз без менеджера
создать нельзя; workflow отклоняет другой объект менеджера.

Стоимость считается по формуле организаторов:

```text
cost = input_tokens / 10 + output_tokens
123 входных + 45 выходных = 12.3 + 45 = 57.3 конкурсной единицы
```

Внутри хранятся целые десятые: `123 + 10 * 45 = 573`. Значения для вывода
представлены Decimal, без арифметики float и ошибок округления. Кеш не даёт
скидки: учитываются все prompt_tokens.

Каждый запрос проходит следующие шаги:

1. Оценивается вход: число UTF-8 байт сериализованных сообщений плюс запас
   1024 токена на служебное оформление. Это консервативная оценка, а не точный
   токенизатор модели. Ограничения размера контекста сохраняются.
2. До отправки резервируется `оценка входа / 10 + max_tokens`. При нехватке
   доступных средств HTTP-запроса нет. Уникальный идентификатор попытки
   защищает от повторного резервирования.
3. При достоверном usage резерв заменяется фактическим расходом, разница
   освобождается. Повторное согласование с теми же числами не списывает их
   снова; согласование с другими числами отвергается.
4. После таймаута, отмены, HTTP-ошибки, отсутствующего или некорректного usage
   весь резерв сохраняется как неопределённый. Новые LLM-вызовы блокируются
   для всего запуска. Неизвестный расход не объявляется нулевым.

При подтверждённой включённой детализации reasoning_tokens уже находятся
в completion_tokens и повторно не прибавляются. При подтверждённой отдельной
схеме складываются completion и reasoning. Без известной схемы ненулевой
reasoning делает учёт неопределённым: резерв остаётся, новые вызовы запрещены.
Для документированных noreason-моделей отсутствие reasoning ожидаемо;
неожиданный ненулевой счётчик также останавливает модельный маршрут.

`manager.snapshot()` возвращает лимит, подтверждённый расход `spent`, занятый
резерв `reserved`, доступный остаток `available`, признак блокировки `frozen`,
число неопределённых попыток, расходы по задачам и неизменяемые записи запросов.
В записях запросов и таблице задач суммы имеют явные имена `*_tenths`.
Ключ задачи — путь её каталога, поэтому совпадающие task_id не объединяют
разные рабочие каталоги. Полных запросов, ответов, URL и ключей в этой
статистике нет. CLI печатает краткую строку `budget_*` после итогов обработки.
Когда frozen=True, доступный для новых запросов остаток равен нулю; spent
по-прежнему обозначает только известные расходы, reserved — занятые оценки.

Резервирование и согласование защищены RLock: конкурирующие обращения
не могут зарезервировать больше общего лимита. Планировщик использует этот же
объект; параллельное исполнение задач пока не добавлено.

Прямой `complete`, fallback и предложение кода проходят через тот же счётчик.
Будущие компоненты должны получать этот же gateway/manager. Дополнительно
публичный callback `LLMCallEvents.LLM_INPUT` установленного openJiuwen
блокирует самостоятельные SDK-вызовы до транспорта. Единственное разрешение
на SDK-вызов связано с уже зарезервированными сообщениями, моделью и лимитом
шлюза и расходуется один раз; это используется в тесте совместимости SDK.
SDK-логирование содержимого сообщений при отказе подавлено.
Это защита маршрутов приложения, не сетевая песочница для произвольного Python.

Локальные math/search/data_analysis/coding продолжают работать при нулевом,
исчерпанном или заблокированном LLM-бюджете. Успешный answer.txt по-прежнему
сохраняется сразу после каждой задачи.

Ограничения до проверки реального провайдера: токенизация и служебная
надбавка сервера могут отличаться от оценки; соблюдение max_tokens на
noreason-моделях проверено только mock-контрактом. Если фактический вход или
выход превышает зарезервированную границу, записывается весь известный расход
и новые вызовы блокируются. Абсолютную гарантию удалённого лимита без
подтверждённого контракта сервера это не даёт. Состояние бюджета хранится
в памяти одного запуска; восстановление после перезапуска конкурсного
процесса ещё не реализовано. Реальный API на этом этапе не вызывался.

## Планировщик задач

`run_agent.py` по умолчанию использует `--strategy priority`. Для сравнения
поддержаны `--strategy original` (порядок имён каталогов) и `--strategy reward`
(убывание награды). Все три режима используют одинаковые решатели, настоящий
workflow openJiuwen, два прохода, правила доверия и полный резерв BudgetManager.
Это сравнение порядка выбора при одинаковых условиях исполнения.

```bash
BUDGET=0 .venv/bin/python -B run_agent.py --tasks-dir /path/to/tasks --strategy priority
.venv/bin/python -B tests/test_planner.py --experiments
```

Два прохода устроены так:

1. Каждая доступная и безопасная задача получает одну локальную попытку.
   В приоритетном режиме сначала идут формулировки, похожие на поддерживаемую
   грамматику, затем остальные. Внутри этих групп сравнивается reward × p_local;
   p_local=0.9 для похожей грамматики и 0.25 для остальных. Это эвристика,
   не измеренная вероятность. Высокая сложность не запрещает дешёвую попытку.
2. После локального отказа проверяется возможность подготовить проверяемый
   fallback-контекст. Нерешённые кандидаты получают приоритет
   `reward × p_success / estimated_cost`. Все локальные попытки завершаются
   до первого платного вызова. Для бесплатной группы нет деления на ноль.

Сложность — прозрачный числовой признак:
`1 + число_числовых_литералов // 3 + число_mentor/employer + число_and/where/through/between + длина // 1000`.
Проверяются наличие workspace, базы Markdown, явно указанного CSV и исходника
с тестом для поддерживаемой coding-инструкции, а также выход путей за workspace.
Содержимое документов не становится инструкциями планировщика. Ни expected,
ни check не входят в объект Task и не участвуют в выборе.

Начальные p_success: math=0.75, search=0.8, data_analysis=0.75, делённые
на `1 + complexity / 10`. Начальный прогноз стоимости — консервативная оценка
входа шлюза / 10 плюс половина запрошенного лимита генерации. Эти числа —
отправные эвристики без заявления о калибровке на финальном наборе.

После трёх подтверждённых запросов одного типа задач и той же модели прогноз
уточняется отношением фактического входа к оценённому и средним фактическим
выходом. Вероятность уточняется смесью исходной оценки с весом 4 и наблюдаемых
успехов/неудач. Неизвестный usage в обучение не попадает. Все реальные расходы
читаются из BudgetManager; второго счётчика токенов в планировщике нет.
Обновление оценок действительно может менять следующую выбранную задачу,
что проверяется отдельным тестом.

Прогноз определяет порядок, но допуск всегда требует полного безопасного
резерва `оценка входа / 10 + max_tokens`. Уменьшение среднего прогноза не
ослабляет этот барьер. После каждой попытки next() снова читает snapshot()
менеджера. При одинаковых данных и бюджете совпадает и порядок выбора;
ничья разрешается по пути каталога.

Состояния различаются:

- `solved` — решение прошло текущую локальную проверку и сохранено;
- `unsupported` — используемые методы не установили ответ;
- `unsolvable` — явно обнаружено деление на ноль в поддерживаемой задаче;
- `insufficient_evidence` — отсутствуют необходимые входы или единственный факт;
- `invalid_data` — повреждённые входные данные;
- `unsafe` — запрещено исполнение либо нельзя установить безопасную границу LLM;
- `deferred` — кандидат отложен по текущему приоритету, это не окончательный отказ;
- `budget_blocked` / `llm_disabled` — нет безопасного резерва или LLM отключён;
- `llm_failed` — единственная модельная попытка не дала проверенного решения;
- `failed` — ошибка исполнения или сохранения, а не доказательство невыполнимости;
- `existing_answer` — прежний файл сохранён, но планировщик не заявляет его проверенным.

Для неподдержанной локальной формулировки дополнительно сохраняется local_outcome,
чтобы поздний запрет бюджета не скрывал первоначальную причину. Отсутствие факта
в поддержанной схеме не объявляется доказательством невозможности произвольной
задачи. Никакого универсального распознавания всех невыполнимых задач здесь нет.

Низкая и даже нулевая награда не являются порогом отбрасывания: такие задачи
получают попытку, если после более приоритетных кандидатов хватает бюджета.
Поддерживается любое число задач, включая 0, 1, 2, 8 и 100. Внутри запуска
успешная задача повторно не выбирается; допускается одна локальная и одна
LLM-попытка. Внутренние ограничения coding-решателя сохраняются.
Без `--trusted-code` coding не исполняется. Локальные решения продолжаются
даже при изначально исчерпанном или заблокированном менеджере бюджета.

`run_tasks(..., report=dict)` дополнительно возвращает через переданный словарь
порядок попыток, итоговые категории, сумму наград проверенных текущим решателем
решений, прогноз расхода и snapshot общего бюджета. Прогнозы не являются
фактическими списаниями. Метрика unsuccessful_attempts включает неудачные
локальные пробы и LLM-попытки; llm_unsuccessful_attempts выделяет вторые.
Выбор без фактической попытки из-за бюджета туда не входит. Итоговая сумма
наград не заменяет проверку скрытыми тестами организаторов.

В дефицитном наборе две короткие задачи вместе выгоднее одной дорогой.
В проигрышном наборе короткая задача получает неверный mock-план, занимает
бюджет и мешает решить длинную. У priority там одна неудачная LLM-попытка;
остальные неудачные попытки в таблице — бесплатные локальные отказы.
Таблица показывает свойства этих искусственных наборов, а не ожидаемый
результат финального конкурса и не доказательство оптимальности эвристики.

Проверены отдельные отборочные наборы из двух локальных и двух модельных
задач, включая вторую с нулевой наградой: 2/2 при достаточном бюджете.
Восемь исходных примеров проверяются только на временных копиях без expected/check:
6/8 в недоверенном режиме, 8/8 с явным доверием к двум предоставленным coding-примерам.
На 100 синтетических задачах с 20 явно неопределёнными делениями на ноль:
80 решённых, 20 пропущенных, расход LLM равен нулю. Хеши исходных материалов
сравниваются до и после проверки примеров.

Для приближения к конкурсному качеству нужны более разнообразные независимые
тренировочные задачи, калибровка вероятностей, расширение покрытия решателей,
проверка реального контракта API и изоляция coding на Docker-этапе. В цикле B
добавлен общий дедлайн и ограничения отдельных операций; это не расширение
покрытия решателей. Заявлять результат 90/100 на скрытом наборе по этим проверкам нельзя.

## Проверки

```bash
.venv/bin/python -B -m unittest discover -s tests -v
.venv/bin/python -m pip check
```

Для отдельной демонстрации шлюза, CLI и совместимости SDK через loopback:

```bash
.venv/bin/python -B -m unittest discover -s tests -p test_llm.py -k LocalHTTPTests -v
```

Эти два теста создают временный сервер только на `127.0.0.1` и случайный
тестовый ключ. Остальные LLM-тесты используют `httpx.MockTransport`.
Реальные адреса и ключи не нужны; реальные LLM-запросы не выполняются.
В среде, запрещающей создание сокетов, для loopback-тестов потребуется
разрешение среды на локальные сокеты; проверки при этом не отключаются.

Этап №6 сохраняет 127 прежних тестов и добавляет проверки менеджера бюджета:
точных дробных списаний, границ резервирования, общего состояния нескольких
задач/шлюзов, конкурентного доступа, таймаутов, отмены, ошибок usage и разных
явно объявленных схем reasoning. Алгоритм расчёта бюджета в тестах настоящий.

Тесты создают задачи во временных каталогах. Проверяются изменённые числа,
порядок операций, округление вниз, нулевой результат, отказ от неизвестных
условий и деления на ноль, игнорирование эталонного поля, исполнение настоящего
workflow, расположение и немедленное сохранение ответа, восстановление после
ошибки отдельной задачи и CLI с нулевым бюджетом и заблокированной сетью.
Поиск дополнительно проверяется на прямых фактах, цепочках связей, изменённых
именах и значениях, независимых базах задач, отсутствующих данных, конфликтах,
постороннем тексте в Markdown и ссылках за пределы базы.
CSV проверяется на изменённых товарах, диапазонах, столбцах и количестве строк,
кавычках и вложенных разделителях, всех агрегатах и сравнениях, пустых выборках,
повреждённых данных и независимых workspace. Все маршруты исполняются через
настоящий workflow openJiuwen.
Для `coding` дополнительно проверяются переименованные функции и файлы,
несколько ошибок, отсутствие частичных правок при неудаче, синтаксические
ошибки, зависание и избыток вывода, неизменность тестов, независимость задач,
лимиты попыток и явное доверие к выполняемому коду.
