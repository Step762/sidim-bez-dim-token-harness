# A1: разбор первой реальной пробы без новых запросов

Источник: существующий `/tmp/neuraldeep-a1-once.json`, прочитан локально.
Оригинальные JSON/Markdown не изменяются. В этой работе HTTP-запросы к NeuralDeep
не выполняются, переменные ключа не читаются. Production-код не меняется.

## Установленные факты

| Уровень | Что подтверждает сохранённый отчёт |
| --- | --- |
| Попытки | 1, только a1_ack; модель qwen3.6-35b-a3b-noreason |
| HTTP | POST, HTTP 200, полностью полученный body: 449 байт |
| API envelope | JSON разобран; 1 choices, строковый content, finish_reason=stop; шлюз не отклонил ответ |
| Модель | Поле model присутствует и совпадает с запрошенным |
| Usage | prompt_tokens=35, completion_tokens=11, total_tokens=46; подтверждён |
| Стоимость | 35 / 10 + 11 = 14.5, без повторного списания |
| Резерв | Был 149, освобождён после расчёта; reserved=0, available=585.5, frozen=false |
| Генерация | Наблюдаемые 11 completion tokens <= max_tokens=32; вход 35 <= оценки 1170 |
| Reasoning | Ненулевые reasoning-счётчики и reasoning_content не наблюдались |
| Содержательная проверка | protocol_reply=false; contract_observed=false |

Поле json_valid=true в событии body_observed относится к ВНЕШНЕМУ API JSON.
Оно ничего не доказывает о JSON внутри message.content. Успех одного маленького
запроса также не доказывает общий серверный предел генерации и будущую стоимость.

## Что восстановить нельзя

Текст message.content в квитанцию не записан. Trace._wire хранил его только в
памяти завершившегося процесса. Событий parsed_plan для этой A1-пробы нет.
protocol_reply объединял strict_json(content), проверку единственного ключа ok
и требование ok is True. Поэтому нельзя различить:

- неверный внутренний JSON;
- корректный JSON неподходящего типа/набора ключей;
- правильный набор ключей, но неверный тип или значение ok.

Нельзя утверждать, что модель вернула конкретный текст, Markdown-ограждение,
false, строку или дополнительное поле. Длительность запроса тоже не сохранена.

## Исправления диагностики

run_a1 теперь сохраняет раздельные diagnostics.http_api/json/schema/value/usage/
generation. Недостижимые проверки имеют null, а не ложное обвинение модели.
Для каждой новой попытки записываются seconds и confirmed_cost; неизвестный
расход имеет null. Старый protocol_reply оставлен как сводный признак.

Намеренно обрезанная третья проба отдельно проверяет length: неполный внутренний
JSON ожидаем и не превращается в ошибку понимания. Production по-прежнему
отклоняет такой ответ; его валидатор не изменён.

Опциональный --capture-a1-response сохраняет ограниченный искусственный ответ
в приватные файлы /tmp, без prompts, headers и API envelope. Подробности защиты
и ограничений приведены в README. По умолчанию текст не сохраняется.

Все проверки одной полученной пробы выполняются перед решением об остановке.
По умолчанию остаётся break при любой неуспешной пробе. Явный флаг
--continue-on-protocol-error позволяет собрать следующие запланированные пробы
при исключительно JSON/schema/value ошибке. Это не retry и не увеличение квоты.
HTTP/авторизация/квота, неизвестный usage, превышение входной оценки или max_tokens,
неожиданный reasoning и сбои сохранения всегда останавливают запуск.

## Как согласовать безопасное продолжение

Уже выполненный запрос входит в исходный лимит 3. Следующие два, если будут
отдельно разрешены: a1_math (max_tokens=64) и a1_limit (32). Никаких повторов ack
автоматически. Оценочные резервы оставшихся проб 188.1 + 156 = 344.1;
с подтверждёнными 14.5 — 358.6. Это прогноз, не гарантия удалённого потолка.
Остаток исходного локального бюджета 585.5; он не обнуляется при новом процессе.

Нужен отдельно проверенный ограниченный runner: прочитать исходную квитанцию,
проверить endpoint/model/runtime/подтверждённый расход, восстановить первую запись
через существующие reserve/settle BudgetManager, запретить повтор a1_ack и разрешить
только два оставшихся ID с единым лимитом 600 и максимумом 2 новых транспортных
попыток. Новый отчёт должен ссылаться на хеш исходного и отличать исторические
данные от новых. При прерывании не повторять автоматически даже неизвестную попытку.

На момент этого разбора live-resume runner ещё не был реализован. Позже добавлен
[отдельный одноразовый runner](A1_RESUME.md) только для a1_math с постоянным
журналом попытки. Реального запуска не было. Обычный CLI cycle_a начинает A1
с начала и не подходит для продолжения. Полный перезапуск — новый эксперимент
с новым явным лимитом запросов, а не продолжение исходных трёх.

Две оставшиеся пробы не восстановят потерянный текст ack. Исходный A1 остаётся
неуспешным и не даёт пропуск в A2. Если важнее повторить ack с захватом текста,
нужно отдельно согласовать замену одной оставшейся пробы либо новый эксперимент.
Ни A2, ни автоматическое ослабление критериев здесь не разрешены.

Старые офлайн-результаты относятся к прежним хешам диагностического кода.
Они сохраняются как исторические; новый live требует новой проверенной
offline-квитанции. Исторический неуспешный A1 не превращается в успешный при
перегенерации офлайн-отчёта.
