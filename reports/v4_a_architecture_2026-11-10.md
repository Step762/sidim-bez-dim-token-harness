### 1.2 Что оценивается — факты регламента

Источник: `codex-local/Регламент соревнования.md`, разделы «Задача участников»,
«Модели и учёт токенов», «Среда выполнения», «Сдача решения», «Порядок оценки».

- Сначала безопасность образа, сборка, затем квалификация: **обе из двух
  выполнимых задач** в выданном бюджете. Вылет на первых трёх этапах — незачёт.
  Нельзя определять особую фазу только по количеству каталогов.
- На полном наборе максимизируется **сумма reward задач, прошедших скрытые тесты**.
  Неверное решение не даёт награды; несохранённое решение тоже не даёт награды.
  При равной награде выигрывает меньший расход токенов.
- Reward назначен случайно и не связан со сложностью. Количество correct само
  по себе не равно цели финального ранжирования. Нулевая награда development-задачи
  не делает её класс бесполезным для квалификации.
- Конкурсная стоимость: `prompt_tokens / 10 + accounted_output_tokens`.
  Reasoning учитывается как output; если уже включён в completion, второй раз
  не прибавляется. Кеш не уменьшает зачтённый input.
- Четыре модели: `qwen3.8-27b`, `qwen3.8-27b-noreason`,
  `qwen3.6-35b-a3b`, `qwen3.6-35b-a3b-noreason`; переключение разрешено.
  Это не подтверждает поддержку reasoning-контракта нашего gateway.
- Реальный openJiuwen и Docker обязательны; без GPU/локальной языковой модели;
  при запуске нельзя скачивать зависимости. Сеть — только разрешённый proxy,
  адрес и ключ через окружение. Промежуточный `answer.txt` рядом с `task.json`
  сохраняется после решения, а не в конце всего набора.
- Сборка ≤1000 s, исполнение ≤1 h, RAM 16 GB; образ <4 GB,
  репозиторий <100 MB без `.git`. Официальная команда использует read-only root,
  writable tasks, tmpfs `/tmp` 2 GB, HOME=/tmp, cap-drop ALL,
  no-new-privileges, pids 512, CPU 8, memory 16g.
- **Неоднозначность самого регламента:** таблица ресурсов говорит CPU ≤4,
  приведённая команда запуска — CPU 8. Для новых экспериментов измерять и на 4 CPU,
  не превращать 8 CPU в безусловную гарантию. Формулировка про пять сессий не
  является явным разрешением на пять конкурентных HTTP-запросов.
- Оценивается последний commit к закрытию; README, фиксированные зависимости,
  отсутствие ключей и доступ жюри к приватному репозиторию обязательны.
  Доступ жюри этим офлайн-аудитом не проверялся.

Уточнения, ранее переданные пользователем от организатора: BUDGET в окружении,
ориентир 100000; четыре типа задач; `expected` отсутствует; использование
`expected/check` для решения запрещено; локальные детерминированные решения
разрешены; прогноз расхода отдельно judge не проверяет. Это отмечено также в
`reports/strategy_4_2_snapshot_2026-11-09.md`, «Основания и степень подтверждения».
100000 не подставляется вместо фактически выданного BUDGET и не объявляется
гарантией бюджета квалификации.

**Неизвестно:** точная проверка дробей, округления, JSON и whitespace скрытым judge,
способ проверки произвольных задач вне примеров, реальное распределение типов и
долей невыполнимых. Наша `benchmark/evaluate.py:compare` сравнивает Fraction,
точный текст и канонический JSON по собственной политике; это **не официальный
judge**. Например, принятие дроби `1/3` нашим benchmark не доказывает её зачёт
в конкурсе. В roadmap новые форматы ответов требуют отдельного подтверждения.

Дополнительный факт из официальных примеров: значение `check` у двух Math и двух
Data — `exact_int`, у двух Search — `exact_str`, у двух Coding — `unittest`.
Это только метки проверки примеров, прочитанные для аудита требований, без
использования `expected` или `check` решателями. Реализации этих проверок здесь
нет; название `exact_int` не раскрывает правила парсинга, а `exact_str` —
правила нормализации. Нельзя переносить их на все скрытые задачи без подтверждения.

## 2. Полный реестр 71 пропуска и граница no-holdout

Требования «полностью разобрать 71» и «не использовать holdout» ограничивают друг
друга: **43 из 71 относятся к holdout**. Выполнен полный реестр ID/тип/reward,
но семантические семьи, точная актуальная причина, сложность и способ решения
этих 43 не извлекались из закрытых условий и не выдумывались.

Источники реестра: свежий development workflow (28 строк), исторический
`diagnostics/results/local-baseline.json` **только поля ID/split/type/reward/status/outcome**,
и записи исходов пар из Q5. Старые holdout-correct (18) плюс три уже явно
зафиксированных в Q5 успешных ID (`math_h15`, `search_h02`, `search_h15`) дают 21,
как в Q5-агрегате. Остальные 43 — реестр пропусков; это реконструкция по истории,
а не скрытый повторный запуск holdout. Содержимое holdout, answer/oracle/family/
rationale/tags и инструкции для этого не использовались.

Reward в таблицах — **назначенная награда**, а не математическое ожидание
получения баллов. Для невозможной задачи ожидаемый прирост равен нулю.
Без измеренной P(success) честного численного E[reward] нет.

## 3. Failure taxonomy: где теряется покрытие

| Слой | Подтверждённая граница | Последствие | Что делать |
| --- | --- | --- | --- |
| Input / safety | Файловые guard, нет workspace, повреждённый CSV, Coding off | Отказ полезен, не считается недостатком грамматики | Сохранить отказ, source snapshot и лимиты |
| Domain | Деление на 0, MIN пустой выборки | Нет числового результата | DomainError, без LLM |
| Meaning completeness | Неизвестный участник, неявный приоритет | Не хватает условий | IncompleteMeaning / AmbiguousMeaning, не угадывать |
| Entity resolution | Квалификатор в вопросе не сопоставляется заголовку | Ложный отказ на search_d12 | EntityRef с явным qualifier и проверкой уникальности |
| Evidence representation | Разные множества полей делают весь профиль конфликтующим | search_d14 не разрешается | Provenance + доказательство identity, без безусловного merge |
| Plan expressivity | Math local имеет cost/power/round/LTR, LLM-схема только начальное число+шаги | Новые локальные классы не компилируются в прежний модельный план | Typed IR и локальные адаптеры; не расширять доверие к модели |

| Diagnostics | math_d13 local_outcome=unsupported, B0 превращает его в budget_blocked | Статус похож на нехватку денег при невозможной операции | В будущем отделить semantic cause от scheduling status |
| Budget / provider | Unknown usage замораживает общий manager | Платные попытки прекращаются, бесплатные продолжаются | Не обнулять резерв и не создавать второй ledger |

**Два подтверждённых ограничения, не названные авариями:**

1. Стабильный Search объединяет конфликт на уровне всей сущности, а не каждого
   факта. Запись Born и отдельная Employer-запись с тем же именем различаются
   по множествам полей. Однако «полезное слияние» требует контракта общей
   идентичности: одинаковое имя само по себе не устраняет одноимённость.
2. `prepare(data)` может построить схему для MIN пустой выборки/отсутствующего
   столбца/повреждённого числа: часть проверки отложена до validate/executor.
   Это **не означает отправку запроса**: текущий harness после подтверждённого
   локального отказа insufficient_evidence/invalid_data до gateway не допускает.
   Новый compiler нельзя подключать в обход этих gates.

В текущем development не найдено корректного пропущенного результата, который
гарантированно исправляется простым увеличением BUDGET или max_tokens.
Из оставшихся 12 не-Coding prepare не делает безопасно решаемыми ни один:
3 Data preflight формально ready, но локально уже доказана причина отказа;
остальные не проходят prepare. Не путать это с ошибкой качества настоящей модели.

### 4.1 Почему не строить «универсальный решатель» сразу

Ограничения executor можно проверить формально на типах/данных; корректность
перевода произвольного естественного языка в IR таким образом не доказывается.
В частности, JSON-schema, валидные цитаты, правильные единицы и даже совпадение
двух вычислений **не доказывают**, что не забыто условие задачи.
Нужны полный trusted разбор ограниченного языка, явная карта покрытия фраз и
отказ при неизвестном смысловом фрагменте. Это ограничивает NL-покрытие,
но сохраняет смысл «Verified».

Не добавлять новых regex для конкретных имён, файлов, годов, answer или ID.
Лексические терминалы ограниченной грамматики допустимы: выигрыш даёт композиция
типизированных операций с общим verifier, а не скрытая таблица исключений.

## 6. Эксперимент №1: точный контракт relation graph

### Вход

`compile_graph_query(instruction, snapshot) -> VerifiedQuery | Refusal`.
`instruction` — только смысловой вопрос и проверенный служебный suffix;
`task_dir` — отдельный guarded каталог задачи. `snapshot` собирается safe_files
по **всей разрешённой KB**, с относительными путями и SHA. Markdown — данные.
Никаких внешних знаний, сети, выполнения Markdown, inferred facts из чужой задачи.
Начальный набор полей: Born/Founded/Headquarters/Mentor/Employer/Alias.
Незнакомые поля сохраняются как неприменимые данные, не как новые команды/связи.

### Факты и промежуточное представление

```text
SourceRef(relative_path, sha256, heading_span, value_span)
EntityRef(canonical_label, explicit_qualifier?, explicit_identity_evidence[])
Fact(subject, predicate, typed_value, sources[])
Query(root, hops=[(predicate, forward|inverse)], projection, cardinality=ONE)
VerifiedQuery(query, instruction_sha256, source_manifest_sha256, coverage)
```

`typed_value`: IntegerYear / ExactText / EntityRef; без float и догадок о типе.
Qualifier распознаётся как явная часть поддержанной формы заголовка/поля,
например `Full Name (profession)`, а не извлекается из внешнего знания.
Query language композирует EntityRef, явный qualifier, разрешённый forward/
inverse hop и конечную проекцию. Никакого произвольного SQL, Python, regex от модели.
Внутренние inverse-операции не выдаются за поля KB.

Граф хранит **все** факты и источники, включая ранние записи, поздние пропуски,
несогласованные значения и aliases. Не использовать overwrite последним документом.
Порядок файлов не является разрешением конфликта. Одинаковые записи можно
дедуплицировать, сохраняя источники; отсутствие поля не означает отрицание.

**Правило identity:** только точное однозначное explicit identity/alias связывание
по принятой схеме. Qualifier участвует в ID; две разные профессии не сливаются.
Одинаковый unqualified heading двух неполных профилей **недостаточен** для
автоматического merge. Для `search_d14` default — отказ до подтверждения схемы
«один canonical heading — одна сущность» или явного identity evidence во входах.
Не менять задание, чтобы искусственно получить это evidence.

### Executor

`execute_graph(query, snapshot, limits) -> Candidate(answer, proof) | Refusal`.
Каждый hop вычисляет конечное множество кандидатов. Inverse — полный просмотр
соответствующего множества рёбер, не первый найденный работник.
Если конечная проекция требует ONE, нужна ровно одна допустимая сущность и
одно непротиворечивое известное значение. Неизвестная связь, влияющая на
уникальность inverse, блокирует ответ; цикл не преодолевается бесконечно.
Ответ — точное исходное значение/уникальный label, без пояснений.

### Независимый verifier

`verify_graph(instruction, candidate, snapshot) -> VerifiedAnswer | Refusal`:

1. Самостоятельно применяет trusted question grammar ко **всему** вопросу,
   сверяет root, qualifier, направление каждого перехода, поле, cardinality.
   Самоподписанный Query/citation от compiler не считается доказательством.
2. Проверяет evidence spans в bounded regular files, SHA и принадлежность
   snapshot этой задаче; на изменении входа — отказ, не применение устаревшего ответа.
3. Пересчитывает путь и условия уникальности через независимый простой
   reference evaluator/полный просмотр фактов. Не вызывает ту же функцию,
   которая предложила Candidate, как единственную проверку корректности.
4. Проверяет отсутствие релевантных противоречий, неизвестных рёбер и alias collisions.
   Несвязанный Born-конфликт не становится разрешением игнорировать Employer-конфликт;
   политика релевантности задаётся явно и тестируется, не «любой удобный факт».
5. Сверяет точное значение и формат ответа. Несовпадение — verifier_reject.

Это независимость относительно candidate/LLM; shared source parser остаётся
частью trusted computing base. Его ошибки отдельно покрываются независимыми
fixture oracle и mutation-тестами. «Два одинаковых алгоритма» не доказывают истинность KB.

### Выход и допустимые отказы

`VerifiedAnswer(answer_text, task_snapshot_hash, proof_digest)` либо
`Refusal(code, stage, safe_detail)`.
Коды: unsupported_meaning, missing_evidence, ambiguous_identity,
conflicting_evidence, invalid_input, resource_limit, stale_snapshot,
verifier_reject. Missing evidence не превращается в unsolvable навсегда.
При отказе answer.txt не создаётся. Только существующий harness.save_answer
публикует успех атомарно и с правами0644.

## 7. Эксперимент №2: Math typed IR без замены stable solver

Контракт: `compile_math(instruction) -> MathIR | Refusal`, затем
`verify_math(instruction, IR)`, `execute_math(IR, limits)`.

```text
Literal(exact_rational, unit, source_span)
Add/Sub(left, right)                # одинаковая размерность
Mul/Div(left, right)                # ограниченная размерностная алгебра
Pow(base, bounded_integer_exponent)
Round(value, places, explicit_mode)
Sequence(initial, ordered_operations)
Return(expression, required_unit, exact_output_policy)
```

Один immutable узел с versioned kind/operands и source spans; нет пользовательских
имен функций, eval/exec и произвольных AST-классов. Рациональные числа, не float.
Cost/fee — композиция quantity×unit_price+fee; once/per_item привязаны отдельным
полным фрагментом. Проценты — умножение на доказанную долю/коэффициент, не add rate.
Порядок before/then и группировка формулы входят в IR, не выводятся по ответу.

Домен units: exact currency codes, count, length, dimensionless; division count
нельзя бездумно трактовать как смену валюты. Нераспознанные единицы — отказ.
Root unit/output policy проверяются независимо. Количество делимых объектов
не округляется без явного floor/rounding; division0 и 0^0 — domain отказ.
Сохранять прежние caps: instruction8000, literal80, AST256, depth32,
value2048bit, power|n|≤64, decimal exponent|n|≤100, round places≤100.
Новые узлы не получают бесконечный ресурс через композицию старых caps.

Verifier независимо восстанавливает структуру задачи из ограниченной
композиционной грамматики, проверяет полное покрытие существенных фраз,
операнды, единицы, порядок и режим округления. Не подтверждать схему по
совпадению множеств чисел или окончательного значения.

Сначала только явные арифметические конструкции и композиции двух уже известных
операций: **никаких новых предположений для трёх оставшихся dev Math-отказов**.
Для неизвестного числа участников переменная не получает нулевое/default значение.
Неоднозначное implicit multiplication не канонизируется без правила.

Предлагаемые файлы следующего этапа: `math_ir.py`, `tests/test_math_ir.py`,
`tests/test_math_ir_workflow.py`. Стабильные math_solver/plan_semantics сначала
использовать только для differential сравнения старых входов; не переписывать.
Adapter к прежнему solver — только после shadow acceptance.

Независимые oracle: ручные Fraction/Decimal формулы, signed ties, exact fee
scope, единицы, permutation/order traps, разрастание промежуточных чисел,
missing clause, scientifically equivalent literals. Минимум12 позитивных
новых композиций и18 negatives, 3 смешанные пары с другими стабильными solver.
Приемлемая точность на finite language проверяется исчерпывающим малым доменом;
свойства без независимого эталона не подменяют correctness.

Go: устойчивый выигрыш на заранее замороженных независимых семействах,0wrong,
никаких утраченных старых ответов в разрешённой regression; CPU/time/memory в пределах.
Timebox3–5ч; если выходит за вечер или требует свободной NL-интерпретации —
ограничить контракт/оставить shadow, а не расширять доверие к LLM.

## 8. Table algebra — конкретный резервный план

Если Graph не докажет identity/уникальность или Math IR окажется слишком велик,
альтернатива — **один compositional boolean filter** над существующим CSV,
а не переписывание всех агрегатов.

```text
Scan(relative_csv, schema_hash)
Filter(And|Or|Compare(column, op, typed_literal))
Aggregate(sum|count_rows|count_value|min|max|avg, column?)
GroupBy(column, Aggregate)
Project(columns) / OrderBy(typed_keys, tie_policy) / Limit(1)
```

В первом резервном срезе — только Scan+Filter+Aggregate, явные скобки,
AND/OR precedence из синтаксиса; без join, arbitrary functions/SQL и inferred types.
Существующие group/top-1 остаются прежними. AST позволяет потом компоновать
операторы без размножения шаблонов. OR считает строку один раз; фильтры не
дублируют вклад при двух истинных ветках. CSV читается streaming стандартной
библиотекой, неизвестные колонки/тип/пустой MIN/повреждённые данные дают отказ.
Модель получает схему и query, не всю таблицу. Выходные форматы зафиксировать;
не вводить новые JSON-массивы до проверки совместимости judge.

Проверять ручными таблицами, SQLite с **явно указанными** типами/NULL/CAST и
сопоставимыми правилами агрегатов; SQLite float SUM не oracle точных дробей.
Показать прирост на новых независимых AND/OR grouping family, не на holdout.
Если прироста нет — отложить Table и потратить вечер на verification/qualification.

## 9. Интерфейсы будущего LLM-as-Compiler

Предлагаемые интерфейсы, **не новая реализованная подсистема**:

1. `TaskSnapshot(task_key, type, instruction_hash, permitted_sources, schema)` —
   без answer/expected/check, только текущая задача; task_key сохраняет directory
   identity, одноимённые ID не объединяют бюджеты/данные.
2. `Capability(schema_version, supported_nodes, limits, required_evidence)` —
   определяется приложением; задача/модель не могут добавить операции.
3. `CompileRequest(snapshot_summary, capability)` → strict JSON `PlanEnvelope`:
   version/domain/typed_program/evidence_span_refs. У каждого поля одна роль;
   duplicate keys, дополнительные поля, произвольный код — отказ.
4. `verify_semantics(instruction, plan, snapshot) -> VerifiedIR | Refusal` —
   проверка полноты смысла независимо от модели, не только schema-valid.
5. `execute(VerifiedIR, snapshot, limits) -> Candidate` и
   `verify_result(candidate, proof, snapshot) -> VerifiedAnswer | Refusal`.
6. Harness-adapter возвращает прежний str/Unsupported*. Единственная публикация
   — прежний atomic save_answer; не давать compiler писать файлы/менять задачи.
7. `gateway.complete(..., task_id=task_key)` использует **тот же BudgetManager**,
   полный безопасный резерв, один вызов, monotonic deadline, no retries.
   В memory production нет durable resume — не обещать его; историческая
   диагностическая durable intent/state защита не переносится и не сбрасывается.
8. Trace без secrets/payload: capability/hash, compile admission/refusal,
   JSON/schema/semantic/execution/result-verifier stages раздельно, usage,
   accounted reasoning, reserve/spent/uncertain, время и publication outcome.
   При timeout/unknown usage общий freeze сохраняется, локальная фаза продолжается.

Для compiler нужны новый finite semantic contract и offline замороженные
правильные/неправильные JSON-планы, а не только увеличение max_tokens.
Модель может предложить IR, но не может «доказать» поддерживаемость новой
естественно-языковой формулировки одной цитатой или своим объяснением.

### 9.1 Время и token economics

Новый Portfolio сначала пробует бесплатный bounded stable solver, затем
допущенный deterministic sidecar и лишь затем платный compiler. Но число локальных
проб тоже ограничено временем/ресурсами: общий production deadline3540s,
sync operation30s, gateway20s по умолчанию; sidecars должны укладываться внутрь.
Правильные ответы сохранять сразу; исчерпание времени не должно удалять их.

При 100 платных задачах средняя стоимость ≤1000 могла бы поместиться в100000;
например, input2000/output512 даёт712 единиц и71200 за100 запросов. Это сценарий,
**не измеренная токенизация/успешность**. Текущий полный safe reserve использует
байтовую оценку с запасом, а не эти произвольные числа. 100×20s=2000s укладывается
в час только без больших накладных расходов; один медленный API/сборка/evidence
не исчезает из времени. Не объявлять токены главным ограничением без трасс.

Исторические реальные трассы: a1_ack14.5 (контракт не подтверждён, текст потерян),
a1_math12.3, development math_d15 129.1; суммарно155.9. Новых трасс нет,
поддержка настоящей модели на Graph/CSV/новом IR не измерена. A2 остаётся
заблокированным; никакой LIVE-команды/разрешения этот отчёт не создаёт.

Сравнение planner: одинаковые frozen independent tasks/reward/time/response tape,
одинаковые IR/verifier/executors; policies original/reward/priority при100000
и тесных бюджетах. Отдельно измерять correct/wrong/reward/2-of-2, paid calls,
semantic admission, reserve/spent/unknown и time. Не собирать новые ответы
настоящей модели для каждого planner; сначала replay. Не обучать прогноз на holdout.
