## 4. Минимальный будущий LIVE-протокол

**Рекомендация: начать с одного нового search_d15, не расходовать все шесть.**
Это предложение следующего отдельно разрешаемого этапа, сейчас он не запускается.

| Параметр одного допустимого запроса | Предлагаемое ограничение |
| --- | --- |
| Модель | Только qwen3.6-35b-a3b-noreason |
| Контекст | Только штатный prepare и выбранные факты этой задачи; без эталонов, секретов и других задач |
| Лимит входа | estimate_input≤2000; фактически для текущего prepare1823. Это UTF-8-эвристика, не доказанный tokenizer bound |
| Выход | max_tokens512, как в проверенном старом pilot |
| Резерв текущего контекста | 1823/10+512=694.3 |
| Локальный общий лимит | BUDGET900 с восстановлением **всех трёх** исторических расходов155.9, без сброса истории |
| История плюс текущий резерв | 155.9+694.3=850.2; допустимый вход2000 дал бы867.9 |
| Таймаут HTTP |20с, retries0, redirects запрещены |
| Общий watchdog |120с, intent должен переживать kill/timeout; незавершённая попытка не повторяется |
| Число новых HTTP |1; остальные пять сценариев0. Это строже заданного максимума6 |
| Права артефактов | Новый приватный каталог0700, отчёт/intent/result0600, успешный answer0644 |

155.9 — исторически подтверждённая локальная сумма, не остаток реальной квоты
аккаунта. Перед запуском её и состояние попыток надо сверить по сохранённой
истории без раскрытия ключей. Нельзя использовать старый history_manager pilot
как будто он учитывает третий запрос: сейчас он восстанавливает только26.8 A1.
Перед будущим вызовом нужно проверить актуальные endpoint/право использования
ключа без печати значений и сверить runtime/manifest. Это здесь не выполнялось.

900 — жёсткий **локальный** лимит ledger;867.9 — условная граница при соблюдении
сервером входного ограничения и max_tokens. Абсолютный потолок удалённого списания
существующим инструментом не доказан. При input выше зарезервированного, выходе
выше max_tokens, неожиданном reasoning, некорректном/отсутствующем usage — учесть
известное, удержать неизвестный резерв и запретить продолжение. Не называть
подтверждённый spent0 при unknown usage бесплатным запросом.

При 401/403/429, иной HTTP/transport-ошибке, timeout, неполном envelope,
несовпадении указанной модели, неизвестном usage/квоте — завершить без следующего
HTTP. Не повторять и length/пустой/неверный JSON/семантически неверный план:
записать отдельную причину, стоимость и остановиться после этого единственного
запроса. Даже правильный ответ требует валидатора и независимой оценки.

В результате раздельно сохранять HTTP status/совместимость, внешний JSON,
внутренний JSON/схему, independent_plan, validator/execute/grade, finish_reason,
input/output и reasoning при наличии, новый/общий подтверждённый расход,
неизвестный резерв и время запроса. Не сохранять ключи, Authorization, production
prompts и сырые ответы модели. Для пяти preflight-отказов usage/time HTTP —
not_called, а не вымышленное измерение модели.

Перед wire: неизменяемый durable claim на фиксированные experiment-id/task-id/
runtime/параметры. Новый output-путь не освобождает claim. Crash после claim,
включая неопределённость отправки, блокирует повтор до ручного выяснения состояния.
Не удалять существующие журналы и не считать новый запуск продолжением старого A1.

## 5. Команды и блокер LIVE

**Рабочей команды настоящего нового эксперимента в текущей версии нет.**
Публиковать вымышленный --task/--Q3 или команду, которая повторит math_d15,
было бы неправильно. Пункт подготовки исполняемой LIVE-команды остаётся незакрытым.

Причины, проверенные по коду:

1. `cycle_a --mode A2 --live` требует успешный полный LIVE A1 для текущих
   runtime/model/endpoint. Полный A1 не пройден; старые runtime-пины устарели.
   Новый passing **mock** offline-отчёт не заменяет LIVE A1.
2. У cycle_a нет CLI для этих шести ID: фиксированная selection12, cap3,
   BUDGET2500; math_d10/math_d11/data_analysis_d10 в неё не входят. Selection
   использует старый baseline: например, Round и C5-CSV теперь уже локальные.
3. `fallback_pilot` разрешает только math_d15, имеет старые history-пины и
   одноразовый журнал уже выполненного опыта. Его нельзя переименовать в новый
   эксперимент сменой output; нельзя сбрасывать state.
4. `run_tasks_diagnostic(live_config=...)` напрямую не является безопасной
   заменой CLI: обычный A2-вызов не обёрнут постоянным per-attempt журналом,
   сохраняет собственный лимит2500 и не восстанавливает полную историю155.9.
   Кроме того, strict_response включён только для старого pilot.

Минимальный следующий технический шаг — **узкое расширение существующего pilot**
для отдельного разрешаемого search_d15: новый experiment namespace без изменения
старых журналов, полный historical ledger, один durable claim, cap1,
strict_response=True, свежая offline-квитанция текущего runtime и запрет повторов.
Trace, DiagnosticGateway, write_once/state_directory, save_answer и оценщик уже
есть. Новый общий runner не требуется. До такого расширения и его офлайн-проверки
LIVE-команду нельзя честно назвать готовой. Старые A1/A2-гейты не отключать.

Точные доступные **офлайн** команды, только новые output-пути:

## 7. Измеряемый прирост и оставшиеся риски

Если будущий отдельно разрешённый Search-пилот даст correct, это подтвердит ещё
один настоящий класс: multi-hop Search через текущий fallback. Потенциальный
прирост относительно local — +1correct/+5 баллов,48/128 и280/503, если затем
подтвердить результат сопоставимой полной оценкой. Два Data-skip не дают баллов.
Фактический текущий benchmark остаётся47/0/81,275/503; нового прироста сейчас нет.

Успешный Search не докажет2/2 квалификацию: в связанной фиксированной паре второй
Math-член требует своего fallback. Исторический correct math_d15 нельзя сложить
с новым запросом и назвать совместным двухзадачным прогоном. Два Math и Search
индексный skip из выборки останутся неподдержанными независимо от числа вызовов.

Блокеры:нет безопасного нового LIVE-entrypoint; gates/история старых опытов;
пять неподходящих для HTTP сценариев; нет положительных нерешённых Data-примеров;
актуальная квота/модель/endpoint не проверены; удалённый потолок input не доказан.
Рекомендуемый следующий этап — разрешить подготовку узкого Search-пилота, затем
отдельно разрешить один настоящий запрос. Для шести положительных сравнительных
вызовов сначала нужен независимый development-набор и отдельный бюджетный протокол.
