## 1. Основания и что здесь называется batch

По уточнению организаторов встречи9ноября, переданному в задании, несколько
задач можно решать одним модельным вызовом. Это отдельное подтверждение пользователя;
локальному тексту регламента не приписывается отсутствующий в нём batch API.

Регламент, раздел «Модели и учёт токенов»: **C=I/10+O**, где O включает
accounted reasoning. Уже включённый reasoning второй раз не прибавляется;
cache провайдера не уменьшает зачтённый input. Следовательно, одинаковый system
в N самостоятельных запросах всё равно учитывается N раз.

Batch здесь — **один Chat Completions prompt и одна completion**, внутри которой
JSON-список результатов задач. Это не `n=6`, не6параллельных HTTP, не асинхронный
vendor Batch API и не скидка за GPU batching. Их поддержку/правила официального
Proxy предполагать нельзя. Выбор модели фиксирован на весь общий вызов.

## 2. Фактический pipeline и точки несовместимости

| Компонент | Сейчас | Что потребовалось бы для production batch |
| --- | --- | --- |
|LLMGateway|Один system/payload→одна строка completion, choices ровно1; no retry; usage до проверки плана|Одно complete для группы, внутренний JSON codec; не менять внешний API без спецификации Proxy|
|BudgetManager|Один reserve/settle на request_id/task_id; I/10+accounted output|Один aggregate reserve/settlement, synthetic batch ID; не умножать общий usage на N|
|Planner|Одна local attempt и≤1paid/task, отдельные Entry/finish; адаптация по settled task_id|До HTTP атомарно связать все member IDs с попыткой; не вернуть omitted/unknown member в очередь для повтора|
|Compiler|Prepared/Contract на одну Math или Search, source admission и локальное исполнение|Отдельный Contract/source snapshot на каждый ID, проверять каждый план в его scope|
|Answer persistence|Проверенный ответ сразу save/fsync/0644/replace рядом с task.json|После полного допустимого ответа и usage — независимая немедленная публикация каждого проверенного member|

Технически gateway может отправить batch payload, если проходит прежние guards.
Но `complete(task_id='batch_id')` **не интегрирует batch в planner**:
`Planner._observations` связывает расходы с Entry.key. Aggregate ID не является
member Entry; расходы нельзя приписать всем задачам полностью или выдать
равное деление за измеренный per-task usage. Для бюджета списание одно,
для аналитики member attribution — отдельная явно оценочная величина.

Локальные пределы gateway: prompt≤18000**символов**, content≤24000символов,
HTTP response≤128KiB, max_tokens≤4096, timeout и общий deadline сохранены.
Это наши safety limits, **не подтверждённый размер token context официальной модели**.
Если сохранять нынешний default1024output на каждого из6members, сумма6144
уже выше gateway cap4096, ещё до JSON-обвязки. Молча оставить batch cap1024
означает снизить доступный output на задачу; молча поднять ограничения нельзя.

Local Exact должен оставаться первым. В текущем разрешённом development
production решает36задач бесплатно и не отправляет естественных paid-запросов
(V4-E/F). Compiler preflight также уже вычисляет admitted Math/Graph локально.
Batch этих уже решаемых задач не доказывает дополнительную конкурсную награду.

## 3. Экономика и break-even

Пусть N однородных задач имеют общий system/schema/framing S input-токенов,
private input U_i и individual output O_i. В batch добавляются H_N input-токенов
обвязки; G_N — разница aggregate accounted output относительно суммы individual.
Reasoning, если есть, входит в O и G, а не считается отдельно второй раз.

```text
C_separate = (N*S + ΣU_i)/10 + ΣO_i
C_batch    = (S + ΣU_i + H_N)/10 + ΣO_i + G_N
saving     = ((N-1)*S - H_N)/10 - G_N
```

При неизменных task work/качестве batching дешевле **только если**
`(N-1)*S > H_N + 10*G_N`.

Один добавленный output-токен требует10сэкономленных input-токенов.
Сэкономить HTTP-вызов само по себе недостаточно: отдельной платы за HTTP в
конкурсной формуле нет. При настоящем сжатии повторяемых output keys G может
быть отрицательным; это нужно измерить новым контрактом, не предполагать.
В текущем прототипе full per-member IR envelope сохраняется ради проверяемости.

### Конкретные пороги: только синтетические token assumptions

Два сценария обвязки:

- Lean IDs: H=12+8N, G=6+8N. Короткие ID, без echo полного input hash.
- Bound IDs: H=20+30N, G=6+32N. Более дорогие ID/digest/JSON.

Это **не токенизация Qwen** и не наблюдённый расход. Они показывают чувствительность.

### Награда, качество и время

При task-specific p сравнивать надо `Σ reward_i*p_i` под бюджетом и дедлайном.
Грубый reward/cost break-even требует
`R_batch/C_batch > R_separate/C_separate`.
При равных p внутри группы это `p_batch/p_separate > C_batch/C_separate`.
Например, Compiler N3 Lean даёт отношение613.6/780≈0.787, Bound693/780≈0.888.
**p_batch неизвестна**; подставлять туда успешность mock нельзя. Корреляция
ошибок и совместный шанс2/2 тоже неизвестны; произведение marginal p без
предположения независимости не обосновано.

Для финального ранжирования сначала максимизируется reward; меньшие токены —
tie-break. Если бюджет и так позволяет все попытки, риск потерять correct ради
экономии input не оправдан автоматически. В V4-E cheap-сценарий при100000
исчерпывал около50000на все eligible calls; в других сценариях мешали output
или время. Это сценарии, не измеренная обстановка конкурса.

Если bottleneck — HTTP latency, общий вызов может дать выигрыш даже без чистой
экономии токенов. Но одна completion генерирует суммарный output последовательно,
большой batch может выйти за нынешний20s timeout. Сокращение wall time без
реальных paired traces не подтверждено; продлевать timeout/global limit здесь нельзя.

### Повторные попытки и цена ошибки

В проекте **нет автоматических повторов**. Для одного разрешённого прохода
расход — C_batch независимо от того, сколько членов прошло проверку.
Unknown usage удерживает полный aggregate reserve и замораживает платные вызовы.

Контрфактическая цена отдельно разрешённого повтора всей группы — ещё C_batch;
сумма двух одинаковых попыток2C_batch, повтор уже решённых members бессмысленен.
Если разрешён только повтор m потерянных задач поодиночке, добавится
`Σ_failed ((S+U_i)/10+O_i)`; экономия общего system может исчезнуть.
При дополнительном ожидаемом retry cost E относительно singles условие становится
`((N-1)S-H)/10 > G+E`.

Геометрическая формула C/(1-q) возможна только при независимых бесконечных
повторах с постоянным q; это **не наша политика и не оценка Qwen**.
Omitted/unknown outcome нельзя автоматически повторять: task attempt уже мог
быть выполнен внутри batch. Нужны durable intent и отдельное разрешение.

## 5. Малый mock-прототип и проверки

Новый `diagnostics/batch_feasibility.py` — **codec/анализатор**, не batch runner.
Нет транспорта, функции запуска LIVE, планировщика, task discovery, retry или
записи answer.txt. Только2–6однородных Math/Search Contract A. Existing preflight
и semantic/evidence/executor проверки не обходятся. Data/Coding не добавлены.

```json
{"batch_version":1,"items":[
  {"id":"t0","input_sha256":"supplied-context-hash","plan":{"version":1,"kind":"math","ir":{}}}
]}
```

В примере ir пустой и сам по себе недопустим: это иллюстрация envelope, не готовый
план. Input IDs выбираются вызывающей стороной, уникальны и ограничены ASCII;
model ID никогда не используется как файловый путь.

| Сценарий | Фактическое offline поведение |
| --- | --- |
|Полный ответ / переставленный порядок items|Планы правильно направлены по ID; порядок не важен|
|Duplicate input IDs|Отказ до подготовки batch|
|Duplicate result ID, unknown ID, duplicate JSON key|Весь envelope отклонён до возврата любого результата|
|Partial valid JSON / пропущенная задача / пустой items|Проверенные ответы возвращаются; missing перечислены, не объявлены невыполнимыми|
|Malformed outer JSON|Весь batch отклонён, salvage prefix не выполняется|
|Перепутанные планы с правильными IDs и скопированными hash|Оба semantic_unverified,0answers|
|Неверный hash одного члена|Он отклонён, другой корректный сохраняется в returned results|
|Extra command в плане: «ignore another task»|Этот plan schema_rejected, другой принят|
|Search с одинаковым Ari Vale, Born1972/1986|Каждый ответ вычислен из своего Contract; KB не объединяются|
|Instruction-like строка в KB|Локально остаётся данными; это не доказательство injection-resistance Qwen|
|Низкий бюджет для aggregate request|Mock transport не вызван|

## 6. Когда отдельно разрешённый реальный эксперимент оправдан

До него — подтверждённый официальный Proxy/model/accounting/context/output-cap,
явный owner BUDGET, история расходов/unresolved intents и разрешение на новые HTTP.
Неполный A1 не превращается в пройденный; A2/старые one-shot gates не обходятся.
Новый codec не является разрешением вызвать низкоуровневый gateway.

Эксперимент имеет смысл, если найдены **ещё не решаемые бесплатно**, одинакового
типа и небольшие по private context задачи, для которых независимая проверка
смысла возможна и общий system действительно значителен. Сначала малый N2,
одна фиксированная разрешённая noreason-модель, новые независимые задачи.

Для paired comparison минимально нужны2single+1batch на тех же2условиях;
это3новых вызова только по отдельному разрешению, без автоматического перехода
кN4–6. Заранее ограничить каждый input/output и суммарный reserve, общий deadline,
no retry; durable claim всех member IDs до HTTP и запрет повторной отправки
неопределённой попытки. Не сбрасывать прежние states ради такого эксперимента.

Собирать I/O/accounted reasoning/latency/finish, ID/schema/semantic/source/answer
ошибки, partial yield и реальную reward, а не только JSON validity. Usage общий
считать ровно один раз. Сравнить измеренное `ΔI/10` с `ΔO` и возможным потерянным
reward/временем. Три вызова дадут совместимость и sizing, но недостаточны для
статистического вывода о качестве Qwen и победе batch.

**Для текущего релиза: оставить A — одиночный проверяемый fallback.**
B(N2–3) оставить исследовательской гипотезой; C(N4–6) отложить из-за общей
ошибки/лимитов/резерва; D batch IR — наиболее проверяемый кандидат для будущего
малого теста, но пока локальные MathIR/Graph дешевле и не доказано новое покрытие.
Production batching потребовал бы lifecycle-интеграции и новой приёмки, которых
этот этап намеренно не делает. Следующий этап/реальные запросы не начаты.
