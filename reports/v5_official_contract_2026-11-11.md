## 4. BudgetManager и контракт Proxy

### Абсолютная единица бюджета

`budget_manager.py:19–25,59–63`:

```text
cost              = input / 10 + accounted_output
internal_cost     = input + 10 * accounted_output
internal_limit    = BUDGET * 10
```

Внутренний целочисленный масштаб в десятых применяется к обеим сторонам.
Поэтому BUDGET=100000 означает 100000 выходных эквивалентов. Ошибки масштаба
в десять раз не обнаружено. Контроль границы: BUDGET=10, input=90, output=1
полностью расходуют 10 единиц, остаток 0. Кеш не вычитается.

Проверки reasoning на моках дали одинаковые 30 единиц при input=100:
completion=20 без reasoning; completion=20, reasoning=7 уже внутри completion;
completion=13 плюс отдельно reasoning=7. Второго списания included reasoning нет.

### Резервы и отказы

Один manager разделяется CLI, planner, workflow и gateway по идентичности объекта.
RLock защищает конкурирующие резервирования. Полный резерв до HTTP равен
`estimated_input / 10 + max_tokens`, а не среднему прогнозу planner.
Settlement идемпотентен. Отмена, transport error, отсутствующий/некорректный usage
оставляют reserve и frozen; новые платные вызовы запрещены. Наблюдённое превышение
input/output не скрывается: расход учитывается, дальнейший бюджет замораживается.
Полученный невалидный ответ всё равно стоит токенов при подтверждённом usage.
Механизм не ждёт остатка или автоостановки Proxy. Локальная работа бесплатна.

**Границы гарантии:** input оценивается как UTF-8 bytes +1024 framing, это не
проверенный официальный tokenizer bound. Локальный timeout не гарантирует отмену
удалённой генерации. Реальный Proxy обязан соблюдать согласованный output cap.
До его подтверждения нельзя обещать абсолютный верхний предел удалённого расхода.

Production manager хранится в памяти одного запуска, не восстанавливает бюджет
после перезапуска процесса и не координирует несколько независимых процессов.
Это не durable экспериментальный ledger. Запускать повторно ограниченный LIVE
пилот через обычный run_agent.py вместо one-shot runner нельзя.

### Фактический wire-контракт

Источник: `llm_gateway.py:17–23,134–195,223–336`.

| Параметр | Реализация | Что ещё не доказано |
|---|---|---|

| Модель | Allowlist из четырёх ID регламента; default qwen3.6-35b-a3b-noreason | Что эти ID сейчас обслуживаются официальным endpoint |

Внешний API JSON и внутренний JSON ответа модели — разные проверки.
После transport/usage проходят strict JSON, схема плана, семантическая проверка
и локальный executor. Успешный HTTP сам по себе не означает правильное решение.
Необязательное поле model, когда возвращено, сравнивается точно; при его
отсутствии ответ не подтверждает фактически обслуженную версию модели.

## 5. Durable one-shot, A2 и старые пилоты

Проверен код и синтетические тесты; настоящее приватное состояние не читалось.

- `diagnostics/a1_resume.py:96–122`: приватный каталог 0700 своего UID,
  O_NOFOLLOW при открытии пути; intent 0600 через O_EXCL, fsync файла и каталога
  **до** возможного HTTP. Создание имени эксклюзивно; не требуется успешный
  JSON-read, чтобы запретить повтор. Разорванный файл/неудачный fsync сохраняют
  запрет. Неопределённый исход после перезапуска не делает слот свободным.
- Resume/recover не повторяет запрос. Повреждение, конкурирующие процессы,
  timeout, неизвестный usage, смена fingerprint и новый output-путь покрыты
  тестами. Старые state-файлы не удалялись и не переносились.
- `diagnostics/cycle_a.py:430–440` по-прежнему требует полный успешный LIVE A1
  с нужными endpoint/model/runtime/diagnostic fingerprints для штатного A2.
  Исторически A1 не пройден; новой успешной квитанции не создавали.
- Публичная история старой отдельной серии: 3 подтверждённых запроса, 155.9
  единиц из 900. Это последнее известное свидетельство из отчётов, **не** новое
  чтение ledger и не проверка текущей квоты/неопределённых запросов.
- Старый fallback/search pilot закреплён за NeuralDeep endpoint и определёнными
  задачами. Это не готовый runner официального Proxy. Подменять URL, отпечатки,
  историю или A1 receipt для его запуска нельзя.
- В чистом клоне Git-игнорируемые state отсутствуют; смена клона не доказывает
  разрешение повторить запрос. В runtime image diagnostics вообще не включены;
  read-only `/app` также не место для записи нового intent. Для следующего
  эксперимента нужен приватный persistent writable путь, не tmpfs /tmp.

### Новые наблюдения, важные для P3

1. **Старые платные цели устарели.** В санитизированной копии проверены ровно
   12 ранее выбранных development-сценариев через настоящий Local Exact, без
   fallback_controls. Десять уже решаются локально, включая math_d15 и search_d15;
   search_d14 отказывается по insufficient_evidence, data_analysis_d11 — invalid_data.
   Естественных LLM-кандидатов в этих 12 сейчас **0**. Это не вывод обо всех
   development-задачах. Код старого Search preflight явно запрещает оплату
   локально решаемой задачи (`fallback_pilot.py:79–84`).
2. **Прямой старый runner в исходном mixed workspace запрещён.**
   `diagnostics/selection.py:44–46` вызывает `benchmark/evaluate.py:38–58`, который
   загружает общий references и читает все task.json. Отбор CHOICES происходит
   позднее и не предотвращает доступ к закрытым входам. Это установлено чтением
   кода, не исполнением на исходном корпусе. Наши проверки использовали физическую
   development-only копию с guard; P3 должен сохранить эту границу или обходиться
   вообще без benchmark, если проба синтетическая.
3. В дополнительной независимой синтетической формулировке «We begin with ...»
   production дал unsupported после semantic preflight: 0 HTTP, 0 расхода.
   Это подтверждает ограниченность текущей грамматики, а не дефект бюджета.
   Не меняли solver/validator и не принуждали его к платной попытке.

### UID — практический риск до получения первого ответа

Dockerfile не задаёт USER; по умолчанию образ запускается от UID 0.
С cap-drop ALL root не получает права обходить произвольные DAC-ограничения
чужого каталога. Mount с флагом rw **не добавляет** Unix write permission.

Для атомарного save нужны: чтение task/workspace, traversal всех родителей,
write+execute каталога каждой задачи. Для чтения результата жюри нужны также
traversal родителей и read самого answer.txt. Одних прав 0644 файла недостаточно,
если родитель закрыт 0700 для другого UID. При запуске от другого UID возможно
такое же несоответствие владельцев и групп; автоматически chmod/chown входов нет.

Свежий WSL probe от UID 1000: первая синтетическая задача в каталоге 0555
не получила answer.txt; следующая записала правильный `45\n` с **0644**;
CLI без BUDGET и OUT завершился exit 1 из-за первой ошибки, сохранив второй ответ.
Это реальная файловая проверка текущего UID, не новый Docker root/non-root тест.
Владелец/организатор должны согласовать UID и права mount на временных копиях;
не следует ослаблять права всего репозитория или конкурсных исходников.

## 9. Готовность Qwen и минимальный P3

**Переходить к HTTP сейчас нельзя.** Официальный endpoint/model contract и
credentials не подтверждены; доступный старый durable runner закреплён за
другим провайдером/устаревшими задачами; нового разрешения с численным лимитом
нет. Старый A2 остаётся закрыт. Успех NeuralDeep не доказывает конкурсный Proxy.

Минимальный следующий шаг — отдельный **P3 Proxy synthetic compatibility pilot**,
без конкурса/benchmark, без Compiler и без новых solver-операций:

| Параметр предложения, ещё не разрешение | Значение |
|---|---|
| Новая уникальная проба | p3_proxy_arithmetic_v1, вопрос `What is 7 minus 3?` |
| Ответ | Внутренний JSON ровно `{"value":"4"}` |
| System | Return only one JSON object with a string field value containing the arithmetic result. |
| Модель | Только qwen3.6-35b-a3b-noreason после подтверждения её ID официальным Proxy |
| Новые HTTP | Максимум 1; redirects/retries/следующая проба запрещены |
| Timeout / max output | 20 секунд /32 токена |
| Новый локальный cap предложения | 200 выходных эквивалентов, если владелец явно разрешит такой scope |
| Input admission | estimate ≤1500, резерв ≤182.0. На подготовленном синтетическом prompt estimate=1217, резерв=153.7; измерено локально, HTTP 0 |
| Защита | Durable exclusive intent+fsync до HTTP, fingerprint endpoint/model/prompt/caps/runtime; при сомнительном исходе только recover, никогда resend |
| Сохранение | Только ограниченный синтетический ответ и безопасные metadata; без ключей/headers; сам журнал на приватной persistent FS, не /tmp tmpfs |

Числа 153.7/182.0 — резерв по текущей эвристике, не проверенный remote tokenizer
bound. Прежде чем называть 200 жёстким удалённым пределом, необходимо получить
контракт подсчёта/лимита генерации и меры Proxy. Одна проба проверит совместимость,
не надёжность ограничителя на всех моделях и не качество решения финальных задач.

Перед P3 необходимо:

1. Получить официальный API-контракт и финальный launcher: BUDGET, units, endpoint,
   модель, max_tokens/usage/reasoning, квоты и сетевую доступность контейнера.
2. Подтвердить владельца/допустимость ключа, не передавая его в чат или исходники.
3. Отдельно авторизовать новый эксперимент и максимум одного HTTP. Определить
   scope бюджета и сверить нераскрываемую историю: есть ли неопределённые
   intent и сколько уже израсходовано на той же квоте. Публичные 155.9 не
   объявлять текущим балансом. Если это прежняя серия 900, расходы должны
   добавляться к ней, а не обнуляться. Если отдельный Proxy/новая квота —
   зафиксировать это явно; не считать переносом разрешения старого A1/A2.
4. В следующем задании минимально подготовить/проверить отдельный durable допуск
   существующими примитивами. Не менять старые receipts, pins или занятые слоты.
   Полный production run_agent.py и прежняя LIVE-команда Search для этого
   не подходят. Проверить повтор процесса, crash до/после HTTP и bad usage на моках.
5. Восстановить Docker WSL Integration вручную и перед контейнерным LIVE
   проверить штатный запуск/права с реальными mount UID. Повторить полный
   Docker acceptance перед финальным релизом; не выдавать P3 за снятие H3 blocker.
6. После единственного разрешённого запроса отдельно оценить HTTP/внешний JSON,
   внутренний JSON, схему, значение, finish_reason, usage, конкурсную стоимость
   и latency. Auth/quota/unknown usage/reasoning/model mismatch/overrun/timeout —
   stop с удержанием неопределённого резерва. A2 и другие пробы автоматически
   не открываются даже после правильного ответа.

Готовой разрешённой LIVE-команды P2 не выдаёт: существующий runner не отвечает
