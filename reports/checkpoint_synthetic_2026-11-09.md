# Checkpoint C5: синтетические fixtures и общее направление Coding

Дата: 9 ноября 2026. Основная ветка `feature/harness-v1`; целевая ветка
направления Coding — `feature/coding-solver`. Работа ведётся в одном общем
приватном репозитории, без отдельного репозитория, ZIP или пакета для Ильи.

## Что исправлено

Три старые fixtures, происходившие из настоящей LIVE-истории, заменены:

- tests/fixtures/a1_ack_synthetic.json;
- tests/fixtures/a1_math_synthetic.json;
- tests/fixtures/a1_math_intent_synthetic.json.

Независимый конструктор tests/synthetic_history.py создаёт минимальные структуры
по схеме валидаторов. Он не читает старые fixtures, /tmp-квитанции или приватные
state-каталоги. Endpoint — `https://synthetic-a1.invalid/v1`, usage — (17,18) и
(29,9), исторические стоимости — 19.7 и 11.9, суммарно 31.6. Это вымышленные
значения. Модель и probe IDs — публичные константы протокола. Нет исходных prompts,
ответов модели, Authorization, ключей, реальных временных меток или endpoint IDs.
Хеши получаются из вымышленных строк и точных сериализаций новых fixtures.
Маркер synthetic_fixture=true явно отличает их от настоящих свидетельств.
LIVE-флаг используется только для проверки схемы, не удостоверяет реальный вызов.

Тестовый helper подставляет пины только в процессах тестов и восстанавливает их
после выхода из контекста. Валидаторы не подменяются: проверяются байты, SHA256,
модель, endpoint, runtime, параметры, usage, бюджет и защита повторов. В обычном
CLI синтетическая квитанция отвергается по исходному pin до сетевого вызова.
Нет CLI-флага или переменной окружения для включения тестового контракта.

В двух диагностических модулях фиксированный usage вынесен в ACK_USAGE/MATH_USAGE;
штатные значения исторического контракта сохранены. Производные стоимости теперь
рассчитываются из того же usage вместо повторения литералов. Source SHA, реальные
пины, разрешённый endpoint, ограничения запросов/генерации и штатные LIVE-проверки
не ослаблены. Эти модули не входят в production Docker allowlist.

Добавлены пять тестов к прежним 488: происхождение fixtures и цепочка SHA,
восстановление тестовых пинов/отсутствие чувствительных полей, отказ штатного
валидатора, отрицательные семантические сценарии resume и pilot. В последних
хеш намеренно согласуется с повреждённым файлом, чтобы проверка действительно
дошла до неверных данных. Для pilot согласуются обе копии и hash: неверные поля
всё равно блокируют попытку. Старые проверки бюджета, unknown usage, авторизации,
повторов, одновременных процессов, crash/fsync и редактирования секретов сохранены.

не исполняется; trusted Coding используется только для известных официальных
fixtures существующего smoke. Недоверенный Coding остаётся выключен.

Production runtime, BudgetManager, LLM gateway и исходный benchmark не правились
при исправлении fixtures. Архитектура/алгоритмы решателей не менялись. Новых
NeuralDeep-вызовов и расхода конкурсных токенов нет. Приватные журналы не менялись; содержимое старых
отчётов сохранено. Старые /tmp-логи прерванного запуска в возобновлённом
окружении недоступны; новые проверки выполняются заново, а не объявляются
завершёнными по памяти.

## Проверки перед публикацией

Явный allowlist: reports/checkpoint_core_2026-11-09.txt и
reports/checkpoint_docs_2026-11-09.txt. Исторические списки C2/C3 сохранены как
отчёты; для staging используются только эти актуальные два списка.
В checkpoint должны входить C1–C5, диагностика, тесты, результаты этапов и handoff,
но не .env,.venv,codex-local,AGENTS.md,секреты,реальные квитанции,state и /tmp.

Аудит истории выполняется по всем доступным refs после fetch origin: каждый
доступный blob проверяется на характерные секреты и JSON-схему LIVE-квитанций,
отдельно проверяются исторические пути. Синтетические fixtures в новом индексе
сверяются с независимым конструктором; реальные квитанции в истории недопустимы.
Это проверка доступной истории и распознаваемых признаков, не обещание обнаружить
любой произвольный неизвестный формат секрета или невидимые серверные refs.

После успешных проверок разрешён один коммит:
`Checkpoint C5 with synthetic fixtures and coding handoff`.
Затем обычный push основной ветки, сверка SHA, создание отсутствующей Coding-ветки
ровно от checkpoint, её push и повторная сверка обеих веток. Без force,merge,
reset,clean и переключения рабочего checkout. Фактический SHA и результат
публикации сообщаются после Git-операций; сам этот документ включается до коммита.

## Работа Coding

PROJECT_HANDOFF_FOR_ILIYA.md содержит архитектуру, workflow, команды clone/tests,
границы изменений и PR в feature/harness-v1. CODING_TASK.md задаёт измеримый
результат отдельного review-only модуля. CODING_ISOLATION.md объясняет ограничения
sandbox и запрет недоверенного исполнения. Development-входы перечислены отдельно;
holdout/эталоны видны в общем репозитории, но не используются для подгонки правил.
Ветка feature/coding-solver принадлежит направлению, а не одному человеку.
Приглашение collaborator отправляет владелец; доступы автоматически не меняются.

## Аудит и подготовка Git

После fetch origin проверены все доступные локальные refs: **9 коммитов,
515 blob-объектов**. Реальные LIVE-квитанции, запрещённые исторические пути
и признаки типичных секретов не найдены. В новом наборе 67 явно выбранных файлов
(40 core,27 документов), около1.2МБ; весь предназначенный для Git набор около4.2МБ.
Перед коммитом проверяются содержимое индекса, реальные имена/размеры, происхождение
fixtures и git diff --cached --check. Исходный benchmark/эталоны и локальные
приватные state-каталоги совпадают с начальным снимком по SHA256.

В WSL не был настроен credential helper. Для Git используется уже установленный
Windows Git Credential Manager через параметр команды, без интерактивного входа,
вывода токенов или изменения постоянной конфигурации. Origin подтверждён;
до публикации feature/harness-v1=854b4da…,main=5fe93cc… . Новая ветка направления
Coding создаётся после успешного push основной. Рабочий checkout не переключается.
Никакие permissions/collaborators/PR автоматически не меняются.
