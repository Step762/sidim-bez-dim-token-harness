## 2. Абсолютная единица бюджета — сверка с кодом

Регламент прямо задаёт бюджет **в выходных токенах**,10входных равны1выходному.
При `I=prompt_tokens`, `C=completion_tokens`, `R=reasoning_tokens`:

```text
C_out = C                  если reasoning уже включён в completion
C_out = C + R              если подтверждён отдельный счётчик reasoning
cost  = I / 10 + C_out     в единицах внешнего BUDGET
```

Неизвестную схему нельзя выбирать по удобству; кеш не уменьшает I.

`budget_manager.py:19–25,46–73` реализует ровно этот масштаб:

```text
cost_tenths = I + 10*C_out
limit_tenths = BUDGET * 10
available = (limit_tenths - spent_tenths - reserved_tenths) / 10
```

`BUDGET=100000` означает **100000 выходных эквивалентов**. Внутренние1000000
десятых — способ точного хранения, а не разрешение потратить1000000выходных.
Например,1000input+125accounted-output=**225единиц**, внутри2250десятых.
10input либо1output стоят1единицу.

Формулы `I/10+O` и `I+10O` сохраняют относительное соотношение цен, но **не имеют
одинаковой абсолютной единицы**: если использовать вторую, бюджет тоже нужно
умножить на10. Код это делает. Сравнить `I+10O` с неизменёнными100000 означало бы
урезать возможности в10раз; сравнить `I/10+O` с1000000 — расширить их в10раз.
Оснований менять масштаб или пересчитывать исторические квитанции нет.

Planner также использует десятые: full reserve через `cost_tenths`,
available×10 при admission (`planner.py:193,243`), прогноз стоимости в тех же
единицах. Его прогнозная половина max_output — эвристика expected cost,
**не** замена полного резерва. Вывод `estimated_cost` делится на10.

`LLMGateway._output_tokens`, `llm_gateway.py:239–263`: included считает C один раз,
separate — C+R, unknown с ненулевым R отвергается. Reasoning-модели до проверенного
контракта total-output cap/usage блокируются до HTTP. По умолчанию используется
noreason-модель. Проверено по тестам included/separate/conflicting counters/cache.

Остаточная неоднозначность встречи: если организатор имел в виду100000 в другой
расчётной единице, это требует **явного официального уточнения**. Сейчас более
точный письменный регламент и реализация согласованы; одной фразы «расчётные
токены» недостаточно для изменения коэффициента10.

## 3. Бюджет, Proxy и немедленное сохранение

### Что работает независимо от Proxy

`run_agent.py:54–79` создаёт один BudgetManager и передаёт тот же объект gateway,
planner и workflow. Несовпадающие менеджеры отвергаются. До HTTP резервируется
**полная** оценка `estimated_input/10 + max_tokens`; при нехватке запроса нет.
Usage учитывается до проверки корректности модельного плана: неверный JSON-план
или семантический отказ не делают уже потраченные токены бесплатными.

После достоверного usage резерв заменяется фактическим расходом, без двойного
списания. При timeout/cancel/HTTP-error/unknown usage неопределённый резерв
остаётся и manager замораживает новые платные вызовы. Локальная обработка не
зависит от положительного model budget. Код не опрашивает остаток Proxy и не
полагается на его остановку как на основной limiter.

Офлайн арифметический probe: BUDGET10, reserve90input+1output исчерпывает ровно10;
следующий reserve отклоняется без транспорта. Unknown cost при резерве150 и
лимите1000 оставляет confirmed spent0, reserved150, available0,frozen=True —
**не** объявляет неизвестный расход нулём и не освобождает850 для новых запросов.

### Предел гарантии

`llm_gateway.py:223–230` оценивает input по UTF-8 bytes+1024, а не по доказанному
токенизатору официального сервера. Контракт удалённого max_tokens и серверного
overhead здесь не проверен. При недооценке/overrun manager зафиксирует весь
известный расход и остановит следующие вызовы, но не отменит уже выставленный
счёт. Локальный timeout не гарантирует отмену удалённой генерации.

Следовательно, локальный limiter реален, но **абсолютная гарантия не превысить
удалённую квоту при нарушенном/неизвестном контракте Proxy не доказана**.
Перед LIVE нужны подтверждённые usage/cap и запас резерва; не подменять их
автоматической остановкой организатора или обещанием токенизации по байтам.
Денежный баланс NeuralDeep и локальный BUDGET — разные вещи, их не смешивать.

State production-менеджера хранится в RAM одного запуска. Перезапуск создаёт
новый менеджер; это не durable resume и не общий ledger нескольких процессов.
Диагностические durable intent/one-shot журналы — другой контур. Нельзя
перезапускать LIVE ради нового локального лимита или обнулять историю.

### Когда появляется answer.txt

`harness.py:304–322`: настоящий workflow завершился → получен проверенный answer →
**save_answer → planner.finish → следующий task**. Ответы не накапливаются до конца.
`save_answer`, строки215–235: временный файл рядом с task.json, flush/fsync,
права0644, проверка identity каталога и атомарный os.replace. Ошибка замены
сохраняет прежний answer; ошибка одной задачи не отменяет другие сохранённые файлы.

Это подтверждено отдельными тестами: файл есть перед следующей задачей и перед
платным вызовом, находится вне workspace, читается хостом, предыдущий ответ
переживает контролируемую ошибку записи. Внутренние counters/logs могут отстать
при убийстве между публикацией и planner.finish; конкурсный артефакт — файл.

**Граница:** если Proxy/организатор остановит процесс ещё во время получения
последнего ответа, его проверки или записи, этот in-flight ответ может не
успеть сохраниться. Уже опубликованные ответы не удаляются. Точное достижение
бюджета последним запросом не даёт гарантии успеть записать результат до kill;
планировать впритык нежелательно. Это не причина ждать Proxy вместо своего учёта.

### Несоответствие инструкции запуска

В приведённой локальным регламентом Docker-команде переданы LLM_BASE_URL/KEY,
но **нет `-e BUDGET`**. Код намеренно включает LLM только при полном окружении
BUDGET+URL+KEY (`run_agent.py:59–65`); без BUDGET остаётся локальный режим.
Здесь подтверждён **стыковочный пробел документа/запуска**, а не доказанная
ошибка BudgetManager. Нужно подтвердить финальную команду организатора и
передачу BUDGET/его единицы. Самовольно подставлять100000 не следует.

## 4. Scoring и planner

`planner.py:193–223,257–315`: paid priority — `reward*p_success/estimated_cost`;
local tier использует native-form/reward/probability и сложность. **Отрицательного
wrong penalty, штрафа за число отказов или отсечения по малому reward нет**.
Нулевая/малая награда не удаляет задачу из очереди; отдельные qualification-тесты
проверяют её обработку. `unsuccessful_attempts` — счётчик отчёта, не вычитаемый score.
Фаза квалификации по количеству каталогов не угадывается.

При отсутствии wrong-штрафа ожидаемая награда попытки — `p_correct*reward`.
Неверный ответ всё равно расходует время/токены, которые могут лишить другой
награды, и портит tie-break при равном reward. Это opportunity cost, не штраф judge.
В квалификации нужна2/2, а не просто больший reward одной задачи.

**Строгий verifier — наша политика качества/безопасности, не требование нулевого
wrong от организатора.** Отсутствие штрафа не требует отключать verifier или
выдавать догадки. Такая смена политики потребовала бы отдельного измерения.
Текущие unsupported/semantic gates могут терять выполнимые задачи, но не из-за
несуществующего штрафного члена в формуле planner.

Эвристики не гарантируют оптимум: ранжирование может отложить большую награду
из-за неверной оценки p/cost, free tier может занять время, полный max_tokens
reserve может не впустить потенциально дешёвую попытку. Это ограничения стратегии,
а не несоответствие scoring. `reward_solved` — сумма локально принятых и сохранённых
ответов, **не подтверждение скрытого judge**. p обновляется по accepted solutions,
а не по доступной истине judge; для нового compiler нужна независимая оценка.

## 5. Gateway, openJiuwen и границы будущего compiler

`llm_gateway.py:134–195,265–336`: URL/key только из окружения в штатном запуске,
POST Chat Completions, один выбранный model, max_tokens, stream=False,
без tools/redirects/env-proxy/retries. HTTP200, choices/message/content,
finish_reason=stop, стандартный usage проверяются; секреты и error body не
публикуются. Единственная попытка на task обеспечивается **planner**, а не
универсальным запретом повторных прямых complete-вызовов. Нативные SDK-вызовы
без зарезервированного permit блокируются callback до транспорта.

Это подтверждённый локальный/NeuralDeep-compatible wire contract, но сообщение
встречи «через официальный Proxy» **не доказывает**, что у него такие же endpoint,
имена/смысл usage/max_tokens/model aliases/лимиты/ошибки. Ошибки контракта fail closed,
но могут сорвать квалификацию. Нужна спецификация именно конкурсного Proxy.

Allowlist включает четыре регламентные модели; один gateway/CLI выбирает одну
на запуск. Две reasoning-модели без проверенного accounting contract фактически
не допускаются. Это безопасное ограничение охвата, не выдуманный запрет правил.
Письменный регламент разрешает переключать модель на любом вызове, а уточнение
встречи оставляет chaining неоднозначным. Пока использовать одну фиксированную
модель; не объявлять multi-model chaining автоматически разрешённым.

Batching нескольких задач, по встрече, **разрешён, но не обязателен**.
Текущий Prepared/validator/task_id/одна попытка обслуживают одну задачу. Это не
нарушение правил. Если batching добавят: один общий reserve/settlement на HTTP,
явное соответствие результатов task IDs, независимая проверка и немедленная
публикация каждого успешного member. Не списывать batch целиком на каждую задачу,
не создавать новый budget на member и не смешивать их KB/CSV. Для первого
Semantic Compiler batching не нужен и не разрешается этим аудитом автоматически.

openJiuwen используется реально: `harness.py:164–212,304–312` строит и исполняет
Start→SolveTask→FallbackTask→End, с WorkflowComponent и отдельной session.
Установленная версия **0.1.20.post1** подтверждена локально. Отдельно прошли
фактический workflow test и настоящий OpenAIModelClient этой версии на loopback
mock через тот же зарезервированный gateway. LLM transport на httpx сам по себе
не нарушает требование «агент на openJiuwen»: вычислительный workflow не имитация.

## 6. Критические gates и решение о V4-D

**К офлайн V4-D Semantic Compiler переходить можно как к следующему отдельно
заданному этапу:** finite IR/schema, source admission, mocks, негативные планы,
одна задача/одна модель/одна попытка, общий manager и прежние gates.
**К LIVE или production-активации сейчас нельзя считать проект готовым.**

Перед ними закрыть:

1. **P0 запуск/Proxy:** реальная передача и единица BUDGET; endpoint, usage,
   max_tokens/total reasoning и обработка исчерпания именно официальным Proxy.
   Небольшая настоящая проверка — только после нового явного разрешения.
2. **P0 semantic admission:** versioned strict IR decoder, units/order/rounding,
   доказательства Search, полное условие и независимые positive/negative oracle.
   V4-C verifier опирается на тот же canonical parser, Graph — на общий source
   parser; ни JSON-schema, ни quote, ни совпавший ответ не доказывают общий NL.
   Новые классы требуют проверенного нового preflight-контракта; старые gates
   нельзя просто убрать или обойти прямым вызовом gateway.
3. **P0 управление попытками:** один manager на все расходы compiler; invalid plan
   не запускает repair/retry автоматически; unknown cost сохраняет reserve/freeze.
   A2 остаётся закрытым по неполному A1. Старые one-shot/runtime fingerprints
   нельзя подделывать/обновлять ради допуска. Штатный CLI не проверяет A1-квитанцию:
   это **не разрешение** использовать его для обхода экспериментальных ограничений.
4. **P0 релизная приёмка:** текущая полная WSL-регрессия V4-C не зелёная
   (730pass/3timing-fail/7no-holdout-skip); новые experiments не активированы.
   Все прежние57 новым полным прогоном не проверялись по запрету holdout.
   Для включаемого compiler нужны разрешённая приёмка, packaging/Docker smoke
   и проверка опубликованных ответов; MathIR пока вне Docker allowlist.

Дополнительно уточнить CPU4 в таблице против CPU8 в команде, точный лимит
квалификации, форматы нецелых/JSON-ответов и режим последовательного выбора моделей.
Не включать unsafe Coding ради2/2; если квалификация содержит Coding, текущая
поддержка не гарантирует её прохождение. Эти ограничения не исправлялись в D0.
Для сдачи также нужны образ<4GB,репозиторий<100MB,доступ жюри к приватному
репозиторию и допустимый commit к закрытию. Их новая Docker/GitHub-приёмка здесь
не выполнялась; ветку сдачи локальный текст однозначно не называет.
