# V2 №4: исследование изоляции coding

Дата проверки: 8 ноября 2026 года. Ветка `feature/harness-v1`, исходная версия
`85f383f`. Это отчёт о локальном окружении и принятом ограничении, а не описание
готовой песочницы. Конкурсный LLM и внешние API не использовались.

**Решение: автоматическое исполнение недоверенного Python остаётся запрещённым.**
Доступность отдельных механизмов защиты подтверждена; достаточность их
проверенной комбинации для полного контракта задачи не подтверждена. Это
не доказательство невозможности построить любую песочницу на этом ядре.

## Что задано и что измерено

Регламент, разделы «Среда выполнения» и «Сдача решения», задаёт внешний
контейнер, ресурсы, разрешённый прокси и сохранение `answer.txt`. В его таблице
указаны 4 CPU, а в Docker-команде — 8. Здесь проверялись 8 CPU по команде и
заданию команды. Окончательный запуск организаторов потребует сверки.

Docker Desktop 29.7.2, Linux `6.6.87.2-microsoft-standard-WSL2`, x86_64.
Образ `sidim-bez-dim:harness-v2-math`, Python 3.12.12, openJiuwen 0.1.20.post1.
Образ не пересобирался: все 15 файлов его runtime совпадают по SHA-256 с
текущим checkout. Добавлены только документация и тесты; они не входят в образ.

В контейнере проверены read-only `/app`, writable tmpfs `/tmp` 2 ГиБ,
временная writable копия `/data/tasks`, 16 ГиБ RAM, 8 CPU, pids-limit 512,
CapEff=0, no-new-privileges=1. Docker socket и `/dev/nvidia0` отсутствуют.
`/sys/fs/cgroup` не доступен для записи. Внешние ограничения относятся ко
всему агенту вместе с подпроцессами, а не к каждой задаче отдельно.

Smoke запускается с `--network none`. Он не проверяет будущую конфигурацию
`hack-net` и её firewall: отсутствие доступа к внешним адресам, кроме прокси,
в конкурсном запуске остаётся условием организаторов. Отдельная песочница
не должна давать тестам доступ даже к разрешённому агенту прокси.

| Механизм | Фактический результат внутри Docker | Чего он не гарантирует |
| --- | --- | --- |
| `unshare`: user, mount, PID, network, IPC, UTS, cgroup | Все семь: EPERM, errno 1 | Нельзя получить обычную вложенную namespace-песочницу таким способом |
| `chroot` | EPERM | Нет отдельного корня файловой системы |
| `setgroups`, `setgid`, `setuid` | EPERM; процесс остаётся UID/GID 0 | Нет разделения агента и теста по UID этим способом |
| Запуск отдельного контейнера с `--user 65534:65534` | Работает; исходник агента всё равно читается | Один непривилегированный UID для всего контейнера не разделяет задачи; это была проба, Dockerfile не менялся |
| Landlock | ABI 3; ruleset, path rule и restrict_self успешно применены | Не скрывает всё дерево файлов, не ограничивает все каналы взаимодействия |
| Landlock, обычное открытие файлов | Свои файлы доступны; внешние чтение, запись, listdir и чтение по symlink: EACCES | Уже открытый внешний файловый дескриптор остаётся читаемым |
| Landlock, метаданные | Внешние `stat` и `readlink` успешны | Полная невидимость внешних путей не обеспечена |
| Дополнительный seccomp BPF | Устанавливается без capabilities; выбранные socket/clone/clone3/setsid/kill-вызовы: EPERM | Диагностический список запретов не является проверенной полной политикой syscall |
| Landlock + диагностический seccomp | Совместимы, ограничения обоих действуют | Внешние метаданные и намеренно открытый заранее дескриптор всё ещё доступны |
| RLIMIT_AS | Запрос 32 МиБ сверх лимита завершается MemoryError | Не разграничивает файлы, секреты и процессы |
| RLIMIT_FSIZE | Файл ограничен 1024 байтами, запись 2048: EFBIG | Лимит размера одного файла не ограничивает сумму всех файлов |
| RLIMIT_CPU | Контролируемый цикл остановлен SIGKILL при лимите 1 CPU-секунда, раньше внешнего timeout | Не заменяет wall-clock timeout и контроль дочерних процессов |
| RLIMIT_NPROC=1 | При UID 0 один контролируемый `fork` всё равно успешен | Нельзя полагаться на этот лимит как на запрет порождения процессов |
| Отдельная группа процессов | Создаётся; короткий дочерний процесс успешно получает другую группу через `setsid` | `killpg` не даёт гарантии уничтожения всех недоверенных потомков |

Пробы не отправляют сетевых пакетов. Socket-проба только создаёт дескриптор;
проверка сигналов использует сигнал 0. Проверка fork создаёт ровно одного
заранее известного ребёнка, который сразу завершается и ожидается родителем.
Проверка CPU — известный цикл в отдельном процессе с внешним timeout.
Landlock использует синтетические canary-файлы. Реальные секреты не читаются.

Номера syscall и структуры проверены по локальным Linux UAPI:
`linux/landlock.h`, `linux/seccomp.h`, `linux/prctl.h`,
`x86_64-linux-gnu/asm/unistd_64.h`. Пробы рассчитаны только на Linux x86_64.
Иная архитектура получает явный `unsupported`, а не положительное заключение.
Результат на хосте не переносится на Docker: например, user namespace на
хосте создаётся, а в конкурсном контейнере — нет.

## Сравнение стратегий

Следующая таблица — техническая оценка, а не требования регламента.

| Стратегия | Безопасность и риск для других задач | Покрытие и баллы | Сложность, время и Docker |
| --- | --- | --- | --- |
| A. Выполнять тесты в полноценной песочнице | Нужны совместно проверенные границы FS, процессов, сети, дескрипторов и ресурсов. Доступности Landlock/seccomp недостаточно | Потенциально самое широкое покрытие coding; существующий поиск исправлений всё равно ограничен | Namespace-вариант здесь блокируется. Альтернатива с Landlock + строгим syscall allowlist требует отдельного bootstrap, проверки всех каналов и совместимости CPython; дорогая разработка и дополнительный запуск на каждую попытку |
| B. Только статические изменения | Отсутствие исполнения убирает прямые атаки Python. Ошибочная правка остаётся риском корректности | Синтаксис не доказывает исправление. В текущей грамматике нет независимого формального контракта; гарантированного прироста баллов нет | Простая замена AST быстра, но доказательная проверка семантики существенно сложнее; совместима с Docker без новых пакетов |
| C. Статическая проверка + исполнение только при доказанной изоляции | Отказ безопасен, пока обе проверки не дают достаточного основания | Может расширяться при появлении доказуемого статического подмножества или полноценной песочницы; сейчас coding-баллы не добавлены | Совместима с текущим ядром агента; нельзя включать исполнение по одному успешному capability probe |

Выбрана консервативная политика C **с закрытым разрешением на исполнение и
без публикации неподтверждённых статических исправлений**. Нового статического
решателя нет: существующий AST-генератор рассматривается как генератор
кандидатов для доверенных тестов, а не как доказательство их правильности.
Произвольный Python не выполняется, новые системные пакеты не нужны.

У `return a - b` и `return a + b` одинаково корректный синтаксис; намерение
определяется спецификацией и тестами. Имена функций, комментарии, число
изменённых операторов и успешный `ast.parse` не заменяют эту спецификацию.
Официальные задачи требуют исправления до прохождения тестов. Без исполнения
или доказательной интерпретации полного поддержанного подмножества нельзя
обоснованно записать `DONE`. Такой интерпретатор в этом этапе не реализован.
Частичные правки не применяются, поэтому не нужен новый механизм их отката.

## Почему доступные примитивы не включают coding автоматически

Landlock полезен и действительно работает; называть его недоступным неверно.
Открытый заранее дескриптор можно устранить корректным запуском чистого
процесса. Сетевые и межпроцессные syscall можно ограничить seccomp. Эти факты
оставляют направление для будущей реализации, но не превращают диагностический
фильтр со списком запретов в готовую песочницу.

Проверенная комбинация не закрывает полный контракт этого задания. В частности,
она сохраняет доступ к внешним метаданным, допускает ранее открытые дескрипторы
и не содержит полного списка допустимых системных вызовов и аргументов для
CPython. Нельзя ограничить путь `openat` простым сравнением строки в обычном
seccomp BPF: указатель на строку не даёт фильтру её содержимого. Самостоятельная
песочница должна согласовать файловую политику с импортами Python, закрыть
унаследованные дескрипторы, сигналы и альтернативные каналы доступа, обеспечить
жизненный цикл всех потомков, общий расход writable-пространства и ресурсов.
Эти гарантии здесь не заявлены и исполнением атак не имитируются.

В обычном режиме сохраняются три независимые защиты:

1. Планировщик помечает недоверенный coding как `unsafe`.
2. Узел openJiuwen не вызывает coding-решатель без явного доверия.
3. Прямой `solve_coding` требует именно `trusted is True`; truthy-значения,
   переменные окружения и поля `task.json` не дают разрешения.

Fallback также не запускает модель для coding. BUDGET=0 и наличие настроенного
mock LLM ничего в этой политике не меняют. Изоляция не подменена формальным
импортом: старые маршруты по-прежнему выполняются через настоящий openJiuwen.

`--trusted-code` — прежний режим для заранее проверенных примеров. Это не
безопасный конкурсный режим. Очистка его окружения не устраняет потенциальное
чтение других процессов и файлов; существующий `killpg` не удерживает потомков,
которые меняют сессию. По напечатанному `OK` нельзя аутентифицировать честное
исполнение произвольного вредоносного теста. Доверенный режим не защищает от
таких атак, и новый отчёт не обещает обратного.

## Повторяемые проверки

Новые `tests/test_coding_security.py` содержат 21 тест. Строки с чтением соседей,
окружения/конфигурации/исходников агента, записью вовне, fork/setsid, сетью,
циклом, огромным выделением памяти и сигналами **никогда не исполняются**.
Моки требуют отсутствия запуска, чтения coding workspace, генерации патчей и
публикации. После отказа обычная math-задача решается и получает ответ 0644.
Проверяются также FIFO, symlink, повреждённый Python, отсутствующий workspace,
самостоятельный workflow, отсутствие LLM-запросов и расхода бюджета.
Ошибка публикации и прерывание ожидания процесса моделируются без реального
вредоносного кода и без отправки сигналов посторонним процессам.

Пять дополнительных **известных безвредных** пар source/tests проверяют
сложение, умножение, минимум, обращение списка и чётность, включая отрицательные
значения и пустой список. Тесты заданы независимо от AST-замен, не изменяются
решателем и повторно запускаются после сохранения. Без доверия: 0/5; с явным
доверием: 5/5. Синтаксически корректные варианты сами по себе успехом не считаются.

```bash
.venv/bin/python -B -m unittest discover -s tests -v
.venv/bin/python -B tests/docker_smoke.py --image sidim-bez-dim:harness-v2-math
```

Smoke дополнен проверкой совпадения runtime-файлов, прав ответов 0644 и
выполнением `tests/coding_isolation_probe.py` в отдельном контейнере с
конкурсными ограничениями. Диагностический скрипт монтируется read-only,
не включается в образ и никогда не используется агентом как разрешение запуска.
`sandbox_confirmed: false` в его JSON — фиксированное ограничение назначения
диагностики, **не вычисленный сертификат безопасности**. Конкретные результаты
системных вызовов находятся отдельно в `experiments`.

Все 278 прежних unit-тестов сохранены без изменения. Полный набор с новыми
проверками — 299 тестов: на хосте 299/299 за 93.513 с, в Docker 299/299 за
206.391 с; полный smoke завершился успешно. `git diff --check` прошёл.
Примеры копируются во временный каталог; `expected`
и `check` удаляются до запуска. Исходные `codex-local/` не изменяются.

Официальные ответы для остальных маршрутов сохраняются: math 389 и 1735;
search 1983 и Osaka; data_analysis 158 и 284. Обе coding-задачи пропускаются
в стандартном безопасном режиме и дают `DONE` с сохранёнными исправлениями
только в явно доверенном. Итого безопасный режим остаётся 6/8, доверенный — 8/8.
Для сравнения безопасный V1 повторно запущен в сохранённом образе
`sidim-bez-dim:harness-v8`: те же 6/8, обе coding-задачи без ответа.
Это не повышение конкурсного результата и не гарантия допуска: отборочная
пара с неподдерживаемым coding по-прежнему может привести к выбыванию.

## Вердикт

V2 №4 завершён как исследование с обоснованным отказом от неподтверждённого
исполнения. Полноценная изоляция недоверенного Python **не реализована**.
Невозможность такой реализации вообще **не доказана**: Landlock и seccomp
доступны, но их проверенных свойств недостаточно для заявленной здесь готовности.
Образ сохраняет размер 976 MB; защита Docker и рабочий код агента не менялись.
Развитие песочницы и переход к V2 №5 требуют нового задания.
