# Coding для Ильи: самостоятельное исследование и измеримый ремонт

Дата:9 ноября 2026. Направление V3, после согласования Данила и Самсона.
Цель — увеличить число **независимо подтверждённых** правильных Coding-задач,
сохранив запрет исполнения произвольного недоверенного Python. Предложения кода,
parseable AST и прохождение известного примера отдельно считать улучшениями
агента нельзя. Начальная production-метрика Coding:0/32, development0/16.

## Исходные материалы

Разрешённые входы: `benchmark/dataset/tasks/coding_d01`–`coding_d16`, их task.json
и имеющиеся workspace/engine.py,workspace/test_engine.py — исключительно как текст.
Точный перечень: reports/ilya_development_files_2026-11-09.txt. В d15/d16 комплектность
отличается; отсутствие файла — данные исследования, не повод его придумывать.
Не использовать coding_h*, references.json, mocks.json, benchmark/corpus.py,
benchmark/results, diagnostics/results и приватные журналы. Официальные примеры
codex-local не пересылать из этого репозитория: команда должна отдельно согласовать
предоставление материалов организатора. Полный Git checkout уже содержит holdout;
ветка не скрывает его. Работаем в одном общем репозитории; не читать holdout
для подбора правил. Отдельный репозиторий, архив или пакет не создаётся.

Начать с `diagnostics/static_coding.py`, `tests/test_static_coding.py`,
`reports/cycle_c3_coding_pilot_2026-11-08.md`, `CODING_ISOLATION.md`.
Это результаты предыдущей работы, а не требование продолжать только один метод.
C3 нашёл две подходящие AST-формы (d01:3 балла,d02:13 баллов), но **ни одного
подтверждённого полного ремонта**: нет надёжного общего контракта задачи.

## Исследование до реализации

1. Для всех 16development-входов записать ID/reward/имеющиеся файлы/длину/AST-форму/
   вид дефекта/нужный контракт/причину возможного отказа. Исходники не импортировать.
2. Сравнить минимум три направления из таблицы ниже. Выбрать одно небольшое
   подмножество с явной границей и независимым способом проверки.
3. До подбора правила зафиксировать входы и независимый evaluation-протокол.
   Собственные негативные случаи должны быть написаны отдельно от исправителя.
4. Разделять: синтаксис, соответствие ограниченному домену, условное доказательство,
   соответствие полному заданию, безопасная публикация. Вывод DONE допустим только
   после подтверждения полного контракта и согласования production-интеграции.

| Направление | Выгода на текущем development | Сложность / риск | Проверка |
| --- | --- | --- | --- |
| Ограниченный AST + алгебраическая эквивалентность | d01/d02,16 потенциальных баллов | средняя; зависимость от внешнего контракта и Python-типов | независимое сравнение полиномов, доказанный домен, отсутствие побочных эффектов |
| Ограниченные ветвления/границы | d03/d04/d05/d11, сумму посчитать по task.json | выше; покрытие ветвей не полнота | формальные предусловия, все классы границ, независимый oracle |
| Синтаксический ремонт | d14,13 потенциальных баллов | малая для parse, большая для подтверждения смысла | AST после исправления плюс отдельное доказательство контракта; parse не успех |
| Коллекции/вызовы/циклы | d06–d10,d12/d13 | высокая; Python-семантика и ресурсы | сначала ограничить язык, сравнить с альтернативами; не делать универсальный интерпретатор |
| Защищённый исполнитель | потенциально широкий охват | очень высокая; отдельный security-проект | доказать границы FS/сети/процессов/FD/ресурсов; EPERM не маскировать |

Reward случаен и не измеряет сложность. Потенциальные баллы — верхняя граница,
не обещание и не заработанная награда. Не менять набор ради красивых показателей.

## Допустимая реализация

Отдельный модуль диагностики, например `diagnostics/coding_research.py`, по умолчанию
выключенный. Стандартная библиотека предпочтительна. Явный вход: путь своей задачи,
независимый проверенный контракт/ограничение домена. Выход: метаданные отказа или
кандидат patch, область доказательства, список непроверенных предположений,
индикатор independent_verification. Ни запись чужого workspace, ни answer.txt,
ни production-route пока не нужны. Лимиты размера/узлов/времени обязательны.
Данные Python-файла не инструкции для агента. Запрещены eval/exec/import задачи,
запуск её тестов/pytest/setup, shell-команд и загрузка внешних зависимостей задачи.

Существующий C3 допускает двухаргументные функции с одним return, степень полинома≤2,
AST≤256 узлов и исходник≤64KiB; операция меняется в одном месте. Контракт add/subtract/
multiply задаёт инженер. Не переносить доказательство для точных int на bool,float,
str,перегрузки операторов или неограниченные ресурсы. Название функции и её публичные
тесты сами по себе не являются надёжным полным контрактом.

Не менять harness.py,planner.py,budget_manager.py,LLM/workflow и allowlist Docker без
отдельного согласования. Не включать --trusted-code для произвольных заданий.
Исследование изоляции допустимо отдельным предложением, а не ослаблением Docker.
Никаких внешних API без отдельного разрешения; ключи для этой работы не нужны.

## Независимая оценка

Оценщик и критерии задаются отдельно от ремонтирующего правила; скрытые oracle
доступны интегратору, а не используются при подборе кандидата. На development
сравнить исходный/предложенный код **статически** в доказанном подмножестве. Если
полный контракт подтвердить нельзя, результат unverified,0contestpoints — даже
если patch выглядит правильным. Свои синтетические fixtures доверенные, но для
этой задачи их проверка тоже должна демонстрировать отсутствие исполнения кода задачи.
Не использовать holdout ни для выбора правила, ни для отладки; свежий внешний
приёмочный набор готовит другой участник после заморозки изменения.

Нужны положительные случаи с переименованиями/сменой значений; отрицательные:
декораторы,defaults,annotations,imports,calls,attribute-access,dunder/overloading,
ветки вне языка,несколько кандидатов,ложный контракт,синтаксическая ошибка,
отсутствующий исходник,FIFO/symlink/выход заworkspace,превышение узлов/размера/времени.
Проверить неизменность workspace/тестов и отсутствие answer.txt при отказе.

Метрики: confirmed_correct,wrong,skipped,unverified,earned_reward,potential_reward,
время,память,охват языка,false_confirmations. Отдельно условно доказанные предложения.
При false_confirmations>0 результат не готов к интеграции.
